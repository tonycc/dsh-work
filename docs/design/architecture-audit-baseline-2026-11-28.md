**状态：** 阶段零第一批（本机只读统计 + 一次性库 SQL 计数）已完成；浏览器首屏、真实运行中的事件循环延迟等需用户在场的项待测（见第 5 节）<br>
**对照文档：** [架构合理性、过度设计与性能全面审核报告](architecture-and-performance-audit.md)<br>
**代码基线：** `main` `2b51ce94`；DSH 锁定 `0.1.2-rc.1`

## 1. 测量方法与范围

| 层级 | 方法 | 数据来源 | 局限 |
| --- | --- | --- | --- |
| A 本机只读统计 | 对本机开发库只执行 `SELECT`；阶段耗时用 `pnpm report:run-timings` | 2026-10-23～11-26 的 371 个 Run、368 个 Attempt；全部 359 个已启动 Attempt 的传输方式为 `acp-stdio`（真实 DSH ACP Worker） | 开发库数据是本机验收流量，不代表生产使用分布；样本量小 |
| B 一次性库 SQL 计数 | `pnpm bench:platform-baseline`：在一次性库上逐条调用热路径，用 `database.ts` 的 `debug` 钩子计数；先打开计数客户端的全部连接（排除驱动建连时的内部类型查询），再串行、单次测量 | 合成数据：1 名员工、10 个会话 × 5 轮 = 50 个 Run，每个 Run 6 个事件、2 条消息 | 只覆盖仓储与鉴权层，不含 HTTP 路由层的额外调用；未接生产才装配的推荐与 Skill 草稿读取；数据量小，不能代替 `EXPLAIN` |

每条结论标注 **实测** 或 **推算**（由实测值按代码分支换算）。

## 2. 结果

### 2.1 流式事件（审核 2.2-1、2.6-1）

- **实测**：每个 Run 的 `assistant.delta` 条数 p50 = 1、p95 = 2、最大 7；单条 delta 文本长度 p50 = 457 字符、p95 = 1,344 字符。当前 DSH 按已提交的整段消息发送，不是逐 Token 增量，与 EX-00 的能力核实一致。
- **结论**：审核中“1 轮 400 chunk → 800 次串行 DB 操作”和前端“逐 delta 全量重解析 Markdown”在当前 DSH 下不成立；只有将来 DSH 改为逐 Token 流式时才会出现（2026-11-23 评估过的 0.2.2 已回退）。这两项应改为“条件性风险”，从高优降级。

### 2.2 SSE 轮询（审核 2.2-2）

- **实测**：单次轮询 = 2 条 SQL（`readEventsAfterEvent` + `getRun`），约 1～2 ms；`authorizeWorkbench` = 3 条 SQL（审核写的是 4 条）。
- **推算**：每个打开的运行流稳定约 8 条 SQL/秒。个人流在有新事件的那一批以及每 15 秒心跳时额外复权，每个 Run 只有约 7 个事件（p50）、端到端 p50 约 24 秒，因此审核中的“~20～24 SQL/s”在当前流量下高估约 2～3 倍。
- **未测**：团队空间会话流（`streamWorkspaceSessionEvents`，500ms）只要有人停留在空间页面就持续轮询，可能是更大的常驻开销，待 B 层补测。

### 2.3 `GET /tasks`（审核 2.1-4）

- **实测**：`listTasks` 在 50 个 Run 时执行 **501 条 SQL**（1 条列表查询 + 50 个 Run × 10 条），本机小数据量下单次约 0.1～0.2 秒。
- **实测**：单个 Run 详情 `getTask` = 11 条 SQL（`POST /runs` 返回 202 前也会调用一次）；生产环境个人会话还会装配推荐与 Skill 草稿读取，至少再多 2 条，基准脚本未接入。
- **实测**：连接池为 9 条时，并发 1 / 3 / 5 个 `listTasks` 的墙钟耗时约 0.1～0.14 / 0.3～0.34 / 0.5 秒（两次运行）。`listTasks` 并行查询 50 个 Run 详情，**单个请求就能占满全部 9 条连接**，并发请求只能排队。
- **结论**：审核结论成立，仍是高优；一次 `GET /tasks` 就会让同一时刻的其他请求、SSE 轮询和事件落库排队，随会话历史增长（个人会话会整段拉取消息）还会更慢。

### 2.4 鉴权（审核 2.1-2）

- **实测**：`authenticateApi`（本地账号会话、GET）= 3 条 SQL，其中 1 条是 `UPDATE authentication_sessions`。
- **推算**：钉钉会话再多 1 条（先查本地会话落空），未实测。
- **结论**：每个请求固定 3 条、含 1 次写入属实；单次很快，收益取决于请求量，优先级中等。

### 2.5 运行期复权审计（审核 2.4-2）

- **实测**：`audit_events` 共 13,882 行，其中 `authorization.runtime` / `success` 10,598 行，占 **76%**；按已完成的 338 个 Run 计约 **31 行/Run**（按全部 371 个 Run 计约 29 行/Run）。
- **结论**：审核结论成立，且是审计表增长的主要来源。

### 2.6 大表增长（审核 3-4）

| 表 | 行数 | 总大小 | 每 Run 约（按全部 371 个 Run） |
| --- | ---: | ---: | ---: |
| `audit_events` | 13,882 | 12 MB | 33 KB |
| `run_events` | 3,535 | 5.8 MB | 16 KB |
| `run_attempts` | 368 | 4.2 MB | 11 KB |
| `messages` | 656 | 1.2 MB | 3 KB |
| `data_protection_gateway_events` | 561 | 552 KB | 1.5 KB |
| `model_gateway_requests` | 566 | 536 KB | 1.5 KB |
| `authentication_sessions` | 152（全部已过期或撤销） | 232 KB | — |
| `tool_audit_logs` | 0 | 24 KB | — |

- **推算**：若每天 1,000 个 Run，`audit_events` 约 33 MB/天（约 1 GB/月），`run_events` 约 16 MB/天（约 0.5 GB/月）。去掉运行期成功审计后，`audit_events` 的行数增速约降到四分之一（按行数推算，未按字节核实）。
- **结论**：“无限膨胀”方向成立，但量级是每月 GB 级、不是紧急风险；先去掉成功审计，清理按审核第 6 节阶段二的流程走。

### 2.7 首字延迟与成果收集（审核 2.4-1、2.4-4）

`pnpm report:run-timings`，员工运行 279 个 Attempt（完成 252、失败 24、取消 3）：

| 阶段 | p50 ms | p95 ms |
| --- | ---: | ---: |
| Worker 进程启动 | 23 | 68 |
| ACP 初始化 | 1,082 | 1,484 |
| Session 就绪 | 96 | 175 |
| 首次输出 | 19,688 | 141,494 |
| 成果收集 | 10 | 632 |
| 端到端 | 23,745 | 220,155 |

- **实测**：冷启动（进程启动 + ACP 初始化 + Session 就绪）p50 约 1.2 秒，约占端到端 p50 的 5%；时间主要花在模型与工具执行上。
- **实测**：成果收集 p95 = 632 ms、最大 876 ms。审核中的“最多拖慢 60 秒”是超时上限，不是实际耗时。
- **结论**：DSH 预热池收益有限，维持阶段三、按需评估；成果提取异步化优先级低。

### 2.8 `manifest` 体积（审核 2.5-2）

- **实测**：`run_attempts.manifest` 的 p50 = 5.2 KB、p95 = 13 KB、最大 76 KB。超过 TOAST 阈值，但“几十 KB”只是少数；统计查询的代价应在数据量上来后用 `EXPLAIN` 确认。

## 3. 对审核优先级的影响

| 审核条目 | 原优先级 | 实测后建议 |
| --- | --- | --- |
| `GET /tasks` N+1（2.1-4） | 高优 | **维持高优**：实测 501 条 SQL，单个请求即占满连接池 |
| 运行期复权写成功审计（2.4-2） | 中优 | **升为高优**：占审计表 76%、约 31 行/Run，改动小 |
| 流式 delta 逐条落库（2.2-1） | 高优 | **降为条件性**：当前每个 Run 只有 1～2 条 delta；DSH 改为逐 Token 流式时再处理 |
| 前端逐 delta 重解析（2.6-1） | 高优 | **降为条件性**：同上；包体积 1.1 MB 部分不受影响 |
| SSE 轮询（2.2-2） | 高优 | **降为中优**：约 8 条 SQL/秒/流；团队空间会话流待补测 |
| 每请求更新会话表（2.1-2） | 高优 | **中优**：每请求 3 条 SQL，单次很快 |
| DSH 冷启动（2.4-1） | 中优 | **维持阶段三**：约占端到端 5% |
| 成果提取阻塞（2.4-4） | 中优 | **降为低优**：实测 p95 0.6 秒 |
| 大表无清理（3-4） | — | 先去掉成功审计，再按流程制定保留策略 |

审核文档中的这些结论尚未修改，待确认后再更新。
