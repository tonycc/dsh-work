# dsh-work 移动端方案（Android 优先）

2026-11-28 定稿。原稿与评审讨论见项目内文档；本文件是仓库内的唯一维护入口，新决策直接改这里。

## 结论

目标已确认：给不用钉钉的人用，体验要明显好于钉钉 H5。因此采用**混合架构：高频页面用 Kotlin + Jetpack Compose 原生实现，低频页面用 WebView 复用现有员工端**。只做 WebView 壳的话界面与钉钉 H5 基本一样，拉不开差距；全部重写又太慢。原生代码与 WebView 共用同一个登录 Cookie，服务端认证不用改成令牌。

- **M0 准备（约 3～4 周）：** 手机与电脑登录并存（`mobile-app` 会话来源）、员工端“Android 容器模式”、移动端接口约定、公网入口、CI 与工程骨架，同时启动推送资质核实。
- **v0.1 内测（约 6～8 周）：** 原生登录、对话列表、AI 同事单聊；群组、通知和其余页面走 WebView；受控下载页分发 APK。
- **v0.2（约 4～5 周）：** 系统推送、长登录 + 指纹解锁、应用内自更新。
- **v1.0（约 5～6 周）：** 群组原生化、原生通知中心与成果预览、真机验收。合计约 4.5～5.5 个月。
- **之后：** 按使用数据逐个原生化低频页；iOS 用 SwiftUI 按同一划分做。

“比钉钉 H5 好”具体指：秒开不白屏、聊天滚动与流式输出顺滑、系统推送点击直达、一周以上免登录加指纹解锁、拍照上传和文件打开走系统原生流程、弱网下仍能看到列表。这些指标写进各阶段门槛。

## 技术方案对比与推荐

推荐 E：混合架构。纯 WebView 壳（A）体验与钉钉 H5 相当，达不到“更好”的目标；全部重写（C/D）要把员工端所有功能再做一遍。混合架构把原生投入集中在每天用的几个页面上。

| 方案 | 界面代码 | 服务端认证改动 | 体验对比钉钉 H5 | 主要代价 |
| --- | --- | --- | --- | --- |
| **E. 混合：Compose 高频页 + WebView 低频页（推荐）** | 高频页原生，其余复用 `workbench-web` | 小：共用会话 Cookie，只需新增 `mobile-app` 会话来源 | 明显更好：聊天、推送、登录都是原生 | 聊天页的 Markdown/流式渲染要原生重做；两套界面风格要对齐 |
| A. Kotlin 壳 + 纯 WebView | 全部复用 | 无 | 相当，只多推送和长登录 | 达不到体验目标 |
| B. Capacitor 打包 Vue | 全部复用 | 需 CORS 或令牌 | 相当 | 同 A，还多一层框架 |
| C. 全量原生 Kotlin + Compose | 全部重写 | 可复用 Cookie，也可改令牌 | 最好 | 工作量最大，每个新功能写两遍 |
| D. Flutter / React Native | 全部重写 | 同 C | 接近原生 | 新语言栈；只在 iOS 时有复用收益 |

方案 E 的结构：

- **原生（Compose）：** 登录与改密、对话列表、AI 同事单聊（v0.1）；群组、通知中心、成果预览（v1.0）。技术栈固定为 Compose、OkHttp、okhttp-sse、kotlinx.serialization、Room、WorkManager、Biometric。
- **WebView（Android 容器模式）：** 员工端识别 App 的 UA 标识与 `window.dshAndroid` 桥，像钉钉容器一样锁定协作模式 B，隐藏顶栏与底栏；下载、文件选择、返回经桥交给原生；群组页返回直接回到原生列表。
- **认证边界：** 原生是唯一登录入口。原生登录后把会话 Cookie 同步到 WebView（不带 `Domain`，按剩余时长设 `Max-Age`，写后 `flush()`，不硬编码生产名 `__Host-dsh_work_local_session`）；WebView 不进入登录、改密页，不执行退出，遇 401 交回原生；所有写请求由 OkHttp 拦截器统一带已登记的 `Origin`。
- **接口约定（已核实）：** 发消息和发起 Run 必须带 `idempotencyKey`；上传是原始二进制 + `X-File-Name` 头；登录需改密时仍返回 200，改密后会换新 Cookie。
- **符合仓库约束：** 不新增执行链路，所有 Agent 交互仍经 Run/Attempt → Runtime Adapter → DSH。

哪些页面值得原生化，由 OBS-S2 已有的页面访问统计决定：移动端访问量前几名且仍在 WebView 里的页面，进入下一轮原生化。

## 里程碑

Android 代码全部由 Agent 开发、用户真机验收，合计约 4.5～5.5 个月；每个阶段的“门槛”不过不进入下一阶段。

1. **M0 准备（约 3～4 周）**
   - 服务端：新增 `mobile-app` 会话来源（新迁移放宽迁移 0129 的 provider 约束，记录设备），手机与电脑并存，本机退出只撤销本机。
   - 员工端：Android 容器模式（锁定 B、隐藏顶底栏、401/下载/改密交给原生）。
   - 接口约定：OpenAPI 文档已删除，v0.1 用到的接口在 Android 工程内手写 Kotlin 模型，并以服务端集成测试为准。
   - 公网入口：白名单补 `page-views`、`client-errors` 与 App 登录，加 `limit_conn`；评估从 4174 改到 443。
   - 工程：Android 骨架、GitHub Actions 签名构建、lint、Robolectric + Roborazzi 截图测试；签名密钥离线备份。
   - 推送：摸底员工手机品牌，对照官方文档核实各家准入与备案软著要求。
   - 门槛：原型里原生登录后打开 WebView 群组页无需再登录，且电脑端不掉线。
2. **v0.1 内测（约 6～8 周）**
   - 原生：登录/改密、对话列表（本地缓存）、AI 同事单聊（流式输出 30～50ms 节流、回前台带 `Last-Event-ID` 重连并对账）。
   - WebView：群组、通知和其余页面；返回键、软键盘、安全区。
   - App 内一键导出脱敏诊断日志；受控下载页分发。
   - 门槛：5～10 人内测一周；列表秒开；流式输出不掉帧。
3. **v0.2 推送与安全（约 4～5 周）**
   - 服务端设备注册与推送投递（与钉钉 DT-S2 共建），华为/荣耀/小米厂商通道；OPPO/vivo 用白名单引导 + WorkManager 兜底。
   - 长登录 + `BiometricPrompt` 绑定 Keystore；未设锁屏的手机不保存长会话。
   - 应用内自更新（SHA-256 与签名校验、防降级）。
4. **v1.0 正式版（约 5～6 周）**
   - 群组原生化（任务卡与执行详情可回落 WebView）、原生通知中心、成果预览。
   - 门槛：主要品牌各 1 台真机 P2 验收留证。
5. **之后与 iOS**
   - 按页面访问统计（`page-views` 增加客户端容器标识后）逐个原生化；iOS 用 SwiftUI + WKWebView + APNs。

## 后端/API 需要的改动

执行链路和 CORS 不动；认证只新增一个会话来源。大部分服务端与员工端改动集中在 M0。

| 改动 | 阶段 | 说明 |
| --- | --- | --- |
| `mobile-app` 会话来源 | M0 | 原先密码登录会撤销其他非钉钉会话、退出会撤销全部来源。新迁移放宽 provider 约束并记录设备；与桌面并存，本机退出只撤本机，改密/重置/停用撤全部；有效期进“平台配置” |
| 员工端 Android 容器模式 | M0 | `ui-mode.ts` 锁定 B、`CollabShell` 隐藏顶底栏、`client.ts` 401 与下载走桥、`SettingsView` 隐藏网页改密 |
| 公网入口 | M0 | `/api/workbench/` 已放行；补 `/auth/workbench/mobile/login`、`/auth/workbench/page-views`、`client-errors`，加 `limit_conn`；若改 443 需改部署脚本并对齐 `X-Forwarded-Host` |
| 下载响应 | v0.1 | 已有 RFC 5987 文件名，补 ASCII `filename=` 回退 |
| 设备注册、推送投递与偏好 | v0.2 | `POST/DELETE /devices`；投递器与 DT-S2 共建，来源包括 `user_notifications` 与群组新消息合并，只推名称级信息，发送前复核权限 |
| App 版本检查 | v0.2 | 最新版、最低可用版、下载地址、SHA-256；APK 放对象存储或独立静态托管，不压 Mac mini 带宽 |
| 管理端设备列表与远程撤销 | v0.2 | 配合长会话 |
| `page-views` 容器标识 | v1.0 | 现在多传字段会 422，需扩展以区分 App 与浏览器 |
| 文档 | 持续 | 功能规则、架构总览第 10 节、`e2e/catalog/` |

若将来要做没有 WebView 的纯原生或开放第三方客户端，再评估 Bearer 令牌认证，需要单独安全评审。

## 风险与待确认问题

已定的决策与仍需确认的事项。未勾选项都不阻塞 M0 开工。

- [x] **目标用户：** 不用钉钉的员工，体验要明显好于钉钉 H5。
- [x] **分发：** 内部 APK，GitHub Actions 签名构建。
- [x] **人力：** 无 Kotlin 工程师，Android 代码由 Agent 开发，用户真机验收。
- [ ] **推送准入（未核实）：** 审核意见称 OPPO、vivo 正式推送须上架其商店，小米需企业内部分发审核，各家普遍要求 App 备案与软著。M0 对照官方文档核实，并在极光、阿里云移动推送、服务端直连厂商之间选定。
- [ ] **员工手机品牌分布：** 决定先保障哪几家推送；纯血鸿蒙无法直接装 APK（未核实）。
- [ ] **会话时长：** 手机长登录 7 天还是 30 天。
- [ ] **公网端口：** 继续用 4174 还是改 443。
- [ ] **侧装拦截：** 各品牌对未备案 APK 可能红屏警告，需要分品牌安装指引。
