# 企业组织架构方案（本地维护或钉钉通讯录同步）

**状态：** 待评审，尚未实施。本文所述能力在实施并通过第 9 节验收前均不可用。<br>
**更新日期：** 2026-10-31<br>
**依据：** 现有身份与授权模型（迁移 0001、0015、0016、0018；`server/src/modules/identity/`、`server/src/modules/authorization/`）、[钉钉接入方案](dingtalk-integration-plan.md)、[功能规则](../development/feature-rules.md)；钉钉开放平台公开文档（接口名、事件名、权限点与配额以实施时官方文档为准，见第 8 节）。

## 1. 现状与目标

**现状：** 平台不支持组织架构树。

- `users.department_id` 是一个自由文本字段，没有部门表，也没有上下级关系。AI Hub 同步时写入的是组织名称；本地注册的账号写入员工自己填的部门。管理端运营统计用 `departmentLabel()` 写死了两个部门名。
- 授权只看三类对象：`user_roles`（角色），`data_scope_grants` 中 `subject_type` 为 `user` / `role` / `workspace` 的数据范围，以及项目空间成员角色。没有按部门授权，也没有向下级继承。
- “部门负责人”（`department_manager`）只是根据 `workbench:manage` 权限显示的一个称呼，没有绑定到具体部门，目前也没有只属于部门负责人的员工端操作。
- 钉钉接入方案（DT1～DT4）规定：平台账号按手机号匹配钉钉用户，不自动建账号，钉钉侧部门不授予平台权限。

**目标：**

1. 每个企业选择一种部门树来源：在平台内**本地维护**，或从**钉钉通讯录同步**（OD6）；
2. 本地维护时，管理员在管理端编辑部门树并给员工分配部门；
3. 钉钉同步时，部门树和员工信息保持更新，入职、调岗、离职都能及时反映；同步时自动创建平台账号，并直接绑定对应的钉钉用户，员工在钉钉内免登使用；
4. 两种来源都可以按部门授权：管理员把角色或数据范围授给某个部门（可选包含下级部门），员工的部门变化后权限随之变化。

## 3. 边界

- **一个企业只有一个来源。** 不在钉钉部门树上叠加本地部门，也不允许本地修改钉钉同步来的部门或成员关系。需要跨部门分组时使用项目空间或角色。
- **授权仍由平台决定。** 部门本身不带任何权限，只有管理员配置的部门授权才产生权限。平台以外的系统只能改变“谁在哪个部门”，不能改变“这个部门有什么权限”。这延续了迁移 0016“身份由外部提供、授权由平台负责”的原则，并做了一处放宽：部门成员关系可以间接影响权限。这一风险及其约束见 6.3。
- **不新增 Agent 执行路径。** 本方案只涉及身份、目录和授权，不涉及 Agent 执行。
- **钉钉不可用时不降级为全部放行。** 同步失败时保留上一次成功的状态，不自动停用账号，也不扩大授权（6.2）。
- **管理端不上公网。** 同步全部由服务端主动连接钉钉（OpenAPI + Stream 长连接），不需要公网回调地址。

## 4. 数据模型

| 对象 | 说明 |
| --- | --- |
| `tenants.org_structure_source` | 部门树来源：`none`（默认，未启用组织架构）/ `local` / `dingtalk`。 |
| `org_departments` | `tenant_id`、`id`、`external_dept_id`（钉钉 `dept_id`，本地维护时为空）、`parent_id`、`name`、`path`（从根到本部门的 ID 路径，用于查询子树）、`sort_order`、`status`（active / removed）、`synced_at`（本地维护时为空）、`updated_by`。每个企业有且只有一个根部门；钉钉同步时根部门对应钉钉 `dept_id = 1`，本地维护时根部门以企业名称命名。 |
| `org_department_members` | `tenant_id`、`department_id`、`user_id`、`is_primary`、`synced_at`。员工可以属于多个部门，每个部门都记一行，其中一个为主部门；钉钉同步时主部门取钉钉返回的第一个部门，本地维护时由管理员指定。 |
| `users` | `identity_provider` 增加 `dingtalk`；`external_user_id` 存钉钉 `userid`；新增 `external_union_id`（钉钉 `unionid`）。手机号写入 `users.mobile`（字段来自钉钉接入方案 DT-S1）。`department_id` 继续作为显示文本，写入主部门名称，使现有列表、搜索和统计代码不需要修改。 |
| `org_department_grants` | 管理员配置的部门授权：`department_id`、`include_descendants`、`grant_type`（role / data_scope）、`role_id` 或 `scope_code` + `scope_value`、`granted_by`、`created_at`。 |
| `org_department_managers` | 管理员确认的部门负责人：`department_id`、`user_id`、`assigned_by`。钉钉返回的主管列表只作为界面上的推荐，不自动写入。 |
| `org_directory_sync_state` | 仅钉钉同步使用。同步状态：最近一次全量对账的开始和结束时间、结果、处理数量、待确认的大规模变更（6.2）、Stream 连接状态与最近事件时间。 |

钉钉绑定：通过同步创建的账号，直接写入钉钉接入方案中的 `dingtalk_user_bindings`，状态为**已确认**，来源为 `directory`。这样站内通知的钉钉投递和免登都可以直接使用。

## 5. 部门树来源

5.1～5.4 适用于钉钉同步，5.5 适用于本地维护，5.6 说明来源的选择与切换。

### 5.1 适用范围

- 组织架构（两种来源）只在**本地身份模式**（`IdentityConfiguration` 为 local）下启用。AI Hub 目录同步会覆盖 `users.department_id`，因此服务启动时如果同时检测到 OIDC/AI Hub 配置和任一企业启用了组织架构，就拒绝启动并报错（OD1）。
- 钉钉同步时，每个企业（`tenant`）对应一个钉钉企业（`corpId`），应用凭据只放在 `.env` 或受管的密钥服务中。
- 同一企业中原有的本地账号（`identity_provider = local`）保留。首次全量同步时，如果某个钉钉员工的手机号与现有本地账号的登录名或 `users.mobile` 相同，不自动合并，而是列入管理端“待处理”，由管理员选择“关联到已有账号”（账号转为 `dingtalk` 来源，保留其历史数据和授权）或“新建账号”。

### 5.2 首次全量与每日对账

1. 从根部门开始，逐层获取部门列表，构建完整的部门树；
2. 逐个部门分页获取成员详情（姓名、手机号、邮箱、所属部门列表、在职状态）；
3. **只有完整遍历成功后**，才在一个事务中写入差异：新增或更新部门、建账号、更新资料和成员关系、标记被删除的部门、停用本次没有出现的钉钉员工；
4. 部分遍历失败时（例如接口限频或网络中断），整次对账作废，不写入任何“删除”或“停用”，下次从头开始。

每日对账的时间可配置，默认在凌晨。对账也用于修复漏掉的 Stream 事件。

### 5.3 Stream 事件增量

服务端通过钉钉 Stream 模式订阅通讯录事件：员工入职、资料变更、离职，部门创建、修改、删除。收到事件后，按事件中的 ID **重新调用钉钉接口查询当前状态**再写入，不直接使用事件中携带的数据，这样乱序和重复的事件不会写入过期内容。事件处理以 `(事件类型, 对象 ID, 事件时间)` 去重。Stream 断线时自动重连；断线超过阈值时在管理端显示告警，由每日对账兜底。

Stream 连接由单一进程负责，与定时任务和通知投递器的单一负责进程模式一致。

### 5.4 离职与停用

钉钉员工离职（收到离职事件，或在完整对账中不再出现）时：账号置为 `disabled`，`local_authorization_version + 1`，使现有会话失效；钉钉绑定置为失效；项目空间成员关系、定时任务和历史内容的处理沿用现有的账号停用规则（功能规则 3.8），不新增规则。员工重新入职时（钉钉 `userid` 不变）重新启用原账号，授权按当前部门重新计算。

### 5.5 本地维护

管理端“组织架构”页提供部门树编辑，所有操作只有平台管理员可以执行，每次变更写审计：

- **部门：** 新建、改名、调整排序、移动到其他上级部门（不能移动到自己或自己的下级之下）。删除部门要求该部门没有下级部门、也没有成员；部门上的授权随删除一起失效（6.3）。
- **成员：** 在部门中添加或移除员工，指定主部门；也可以在员工详情中批量调整其所属部门。员工可以不属于任何部门，此时只有直接授予的权限。
- **员工账号：** 仍按现有方式由管理员创建或员工自行注册，不因组织架构而改变。员工注册时自己填写的部门文本**不会**映射为部门成员关系，部门成员关系只能由管理员分配，因为成员关系会带来部门授权。
- **显示字段：** `users.department_id` 由平台写入主部门名称，不再接受员工或管理员直接编辑；未分配部门时沿用现有“未分配部门”的显示。
- **从现有部门文本生成部门（可选，一次性）：** 首次启用本地维护时，管理端可以把现有员工的部门文本去重后生成一层平铺的部门，并把员工分到对应部门。生成前展示预览，由管理员确认；生成后由管理员整理成树。

部门移动、成员变化和删除都会按 6.1 触发权限重算。本地维护的变更都是管理员的明确操作，不适用 6.2 的大规模变更拦截，但移动或删除覆盖较多员工的部门时，确认框显示受影响的人数。

### 5.6 来源的选择与切换

- 平台管理员在管理端为企业选择来源，`none` 可以改为 `local` 或 `dingtalk`。
- 首版**不支持**在已有部门数据后切换来源（`local` ↔ `dingtalk`），因为部门 ID、成员关系和部门授权无法自动对应。确需切换时需要单独设计迁移方案。
- 改回 `none` 时，所有部门授权失效并重算权限；部门数据保留，用于审计。

## 6. 部门授权

### 6.1 生效方式：物化到现有授权表

现有代码中有十多处直接读取 `user_roles` 和 `data_scope_grants`（工作台授权、Runtime 授权、项目空间公共数据范围、Agent 受众上限、管理员判断等）。为了不修改这些读取逻辑，部门授权**物化**为现有的授权行：

- 角色：写入 `user_roles`，`source_key = 'department:<grant_id>'`。迁移 0016 的约束 `source_key = 'local'` 放宽为 `'local'` 或 `'department:%'`。
- 数据范围：`data_scope_grants` 新增 `source_key`（默认 `local`），部门授权写入 `subject_type = 'user'`、`source_key = 'department:<grant_id>'` 的行。唯一约束加上 `source_key`；管理端“替换员工数据范围”只删除和写入 `local` 来源的行。
- 管理端显示每条授权的来源（直接授予 / 来自某部门），部门来源的授权只能在部门授权中修改。

**重新计算：** 以下情况会触发对受影响员工的重新计算——部门授权的增删改、员工所属部门变化、部门在树中移动或被删除。重新计算在同一事务中对比计算前后的授权集合，只写入差异；只有有效权限确实变化时才 `local_authorization_version + 1`，并写一条审计（原因：部门授权变更 / 部门调整 / 同步）。

### 6.2 防止错误的大规模变更

本节只适用于钉钉同步。如果钉钉应用的通讯录权限范围被收窄或误配置，同步结果看起来会像大量员工离职或部门被删除。规则如下：一次对账或一批事件中，如果将停用的账号或将移除的部门授权覆盖的员工超过阈值（默认为当前在职员工的 10%，可配置），就暂停写入这部分变更，在管理端显示“待确认的大规模变更”，由管理员确认后再执行。其余变更正常写入。

### 6.3 风险与约束

部门授权意味着调整某人的部门就会间接改变其平台权限。本地维护时这类调整由平台管理员完成；钉钉同步时则由钉钉管理员完成，平台无法事先审核。约束如下：

- 部门授权只能由平台管理员配置，每次变更写审计；
- 管理端可以查看任意员工的“有效权限及来源”，也可以查看“某条部门授权当前覆盖的员工”；
- 部门被删除时，其授权保留但标记为失效，不转移给上级部门，并在管理端提示处理。

### 6.4 部门负责人

管理员在管理端为部门指定负责人（钉钉同步时，钉钉主管列表作为推荐）。目前员工端没有只属于部门负责人的操作，所以首版只记录负责人关系并在界面上显示，**不新增按部门范围生效的管理权限**。以后如果新增“负责人查看本部门及下级的用量”等功能，按“本部门 + 下级部门”的子树判断，并在设计该功能时单独评审。

## 7. 登录与使用入口

本地维护的企业，登录方式不变。以下内容适用于钉钉同步的企业。

- **钉钉内免登：** 沿用钉钉接入方案 4.3：`POST /auth/workbench/dingtalk/login` 用授权码换取钉钉 `userid`，找到 `identity_provider = dingtalk` 且 `external_user_id` 一致的有效账号后签发员工端会话，并写审计 `login_method = dingtalk`。同步创建的账号绑定状态已是“已确认”，不需要验证码。钉钉移动端和钉钉桌面客户端都通过 H5 微应用进入；手机端访问依赖钉钉接入方案的公网入口（DT2），在办公网内使用钉钉桌面客户端则不依赖公网。
- **系统浏览器：** 不新增钉钉扫码登录（OD2）。`dingtalk` 来源的账号默认没有密码；管理员可以在管理端为某个员工另设登录密码（OD5），该员工之后就可以在系统浏览器中用账号密码登录。
  - 登录名默认用钉钉同步来的手机号，管理员也可以另行指定；登录名与密码规则、初始密码下发和员工修改密码，沿用现有本地账号凭据（`local_user_credentials`）的规则。现有代码只允许 `identity_provider = local` 的账号使用凭据，需要放宽到 `local` 和 `dingtalk`。
  - 设置密码不改变账号的来源：员工资料、部门和在职状态仍以钉钉为准。员工离职被停用后，密码登录同样被拒绝；重新入职恢复账号时，原有密码不自动恢复，需要管理员重新设置。
  - 管理员可以随时收回密码；设置、重置和收回密码都写审计，登录审计中记录 `login_method = password`。
- **管理员：** 管理端仍使用现有的本地管理员账号登录，不使用钉钉身份。

## 8. 待评审确认的默认值与风险

1. **密码的设置范围：** 按 OD5，由管理员逐个为员工设置密码，不提供“给全体员工开启密码登录”的批量操作。如需批量开启，另行确认。
2. **钉钉接口与权限点：** 需申请通讯录只读权限（部门、成员、手机号）和通讯录事件订阅。部门和成员接口的分页、限频，以及事件名称，在 ORG-S3 开始前按官方文档核对。手机号属于敏感字段，只用于显示和 5.1 的账号关联，不出现在员工端搜索结果中。
3. **钉钉应用的通讯录可见范围：** 只能同步应用可见范围内的部门和员工。可见范围需覆盖全公司，否则不在范围内的员工不会有账号；范围被收窄时由 6.2 拦截。
4. **大规模变更阈值：** 默认 10%，需结合企业规模确认。
5. **主部门：** 默认取钉钉返回的第一个部门作为主部门，只影响显示，不影响授权（属于任一部门都会继承该部门的授权）。
6. **项目空间：** 员工的部门授权发生变化后，所在项目空间的公共数据范围会随之变化。这与项目空间“空间不扩大员工权限”的规则一致，无需新增规则。
7. **来源切换：** 首版不支持 `local` ↔ `dingtalk` 切换（5.6）。如果企业先本地维护、后来改用钉钉，需要另做迁移方案。

## 9. 验收

- **P0：** 冒烟服务提供测试身份和内存中的部门树，钉钉客户端使用测试替身，验证管理端部门树编辑、同步状态、部门授权和待处理列表页面可用。
- **P1（本地维护）：** 使用专用 PostgreSQL，覆盖以下场景：新建、改名、移动部门，并拒绝移动到自己的下级之下；删除有成员或下级的部门被拒绝；分配和移除成员、指定主部门后，权限和显示字段随之变化；移动部门后整棵子树的成员权限重算；员工注册时填写的部门文本不产生成员关系；从现有部门文本生成部门（含预览与确认）；已有部门数据时拒绝切换来源；改回 `none` 后部门授权失效。
- **P1（钉钉同步）：** 使用专用 PostgreSQL 和钉钉测试替身，覆盖以下场景：钉钉来源的部门树和成员关系在平台内不能编辑；首次全量建树建号；部分遍历失败时不停用任何账号；乱序或重复事件以查询结果为准；离职后停用账号且会话失效；重新入职后恢复账号；部门授权含与不含下级；调岗后权限变化且权限版本递增；大规模变更被拦截并在确认后执行；管理员替换员工数据范围不会删除部门来源的授权；免登只接受有效的钉钉来源账号；钉钉来源账号设置密码后可以用密码登录，停用后密码登录被拒绝，收回密码后不能再用密码登录；与本地账号手机号冲突时进入待处理。
- **P2：** 使用真实钉钉企业内部应用和真实通讯录，验证全量同步、Stream 事件增量、离职停用、钉钉内免登和部门授权生效，按发布流程留证。测试替身和 P0/P1 的绿灯不能代替 P2。
