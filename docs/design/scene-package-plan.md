## 1. 背景与目标

企业里有一类反复出现的工作：按固定周期从业务系统取数，按确定的规则算出需要处理的事项，分给具体的人，并跟踪处理结果。欠料风险预警是第一个例子，来料检验异常、价格协议到期、应收逾期属于同一类。

现在的平台做这类工作有三个缺口：外部数据只能由模型调用 MCP 取得；每次触发都会创建 Run 并唤醒模型；结果停留在该次 Task 中，主动任务只有一个接收人。若为每个场景单独建业务应用，又无法复制，也用不上 Agent 的配置组合能力。

目标：

- **新场景只靠场景包和配置上线：** 写一个场景包（方法、计算脚本、场景声明），必要时在共享数据服务中增加查询，再配置一条主动任务。不新建服务，不新做页面。
- **程序做确定的事，模型做判断：** 取数、计算、条件判断与交付由平台程序执行；说明与方案排序由 AI 同事经 DSH 执行。
- **结果变成有人负责的跟进项：** 按人分发，与上一次结果对账，标出新增、变差与持续，接收反馈，处理完或不再出现时关闭。
- **欠料风险预警作为首个场景走通，**分期见第 10 节。

| SP8 | 跟进项通知的合并方式 | (a) 每人每次运行合并为一条（标题写紧急条数，正文写新增与变差条数），只在有新增或变差时发送；(b) 新增紧急项另发一条 | (a)。按 NC1 只收与本人相关的事件，按 NC6 不为“无变化”发通知 |
| SP9 | AI 同事输出不合格时 | (a) 跟进项照常交付，不带说明与排序，运行记录标注原因；(b) 整次交付失败 | (a)。事实与候选方案来自程序，AI 说明缺失不影响跟进项的正确性。只适用于 Run 已成功结束的情况；Run 未能创建或失败时不交付，分界见 6.8 |

## 4. 边界

- 不建设通用工作流引擎：固定“取数 → 计算 → 条件判断 → Agent 执行 → 交付”五段，每段只执行一次，没有任意分支、循环或多 Agent 编排（规范 1.1）。Agent 段不能省略。
- 不写外部业务系统：程序步骤只调用标记为“可供程序步骤调用”的只读工具；对外部系统的写操作只在 DSH 中经授权执行，且真实 Agent 审批固定为 `never`，第一期不开放。
- 第一期只在管理员配置的 Agent 主动任务中提供；员工本人的定时任务不支持场景包。
- 不新增钉钉推送；钉钉工作通知随[钉钉接入方案](dingtalk-integration-plan.md) DT-S2 另行规划。
- 欠料二期事项（供应商协同、联动排产、挪用其他订单库存）不在本文范围。

| 能力 | 现状 | 缺口 |

## 6. 方案

### 6.1 总体结构

```
场景包（Skill，管理员发布）           共享数据服务（只读 MCP Server，按业务系统建设）
  SKILL.md   给 AI 同事的方法             erp：建议计划、采购单、货源清单与库存……
  compute/   计算脚本                     srm：确认交期、发货与到货、供应商表现……
  scene.yaml 场景声明
         │ 被 Agent Version 选用                    │ 由 Connector 登记，工具逐个标记
         ▼                                          ▼
主动任务（部署）：固定 Agent Version · 逻辑名绑定 · 参数 · 接收范围 · 放权阶段 · 日程
         │ 触发
         ▼
受理（授权复核并冻结）→ 取数（MCP 客户端）→ 计算（一次性容器）→ 条件 → Run/Attempt → DSH → 交付
                                                                                      │
                                                     跟进项（对账、按人分发、通知、反馈、问 AI）
```

### 6.2 场景包格式

场景包是普通 Skill 包加两样东西：

```
SKILL.md          给模型的方法（frontmatter 照旧）
scene.yaml        场景声明，平台读取
compute/          计算脚本与样例输入；不登记为模型可调用的入口
  risk.py
  samples/        样例输入与期望的输出字段
```

`scene.yaml` 的内容（字段名在 SP-S1 定稿）：

| 部分 | 内容 |
| --- | --- |
| `data` | 用到的数据工具逻辑名与查询参数，如 `erp.suggestion_plan_open`；参数只能引用 `params` 与触发信息，不能引用其他查询或计算的结果；每个查询的数据刷新时间字段与新鲜度要求（6.5）；去重键字段到查询参数的映射（单条重新取数时使用）。不写 Connector ID、地址或凭据 |
| `compute` | 入口（`compute/` 下登记的 `.py`）、需要读取的反馈字段、输出字段定义、样例输入位置 |
| `condition` | 从平台固定的判断方式中选择，只引用输出字段，如“风险行数大于 0” |
| `agent` | 交给 AI 同事的字段子集、每次最多条数与排序依据、输出文件的约定（6.8） |
| `follow_up` | 跟进项模板：标题、事实字段及类型（文本、数量、日期、日期对比、表格、候选方案）、分组字段；去重键；接收人字段；判定变差的字段与比较方式；误报或“不再处理”后重新打开所依据的字段与比较方式 |
| `actions` | 反馈动作：类型（填写字段、选择候选、带原因关闭）、字段、结果状态、是否立即重新取数、字段是否作为计算输入 |
| `params` | 可调参数的名称、类型、默认值与允许范围 |

**计算脚本的目录约定：** 沿用一次性容器的固定挂载，与 `python_execute` 经环境变量给出路径的约定不同。`/skill` 是场景包目录（只读、工作目录）；`/input` 下有 `fetch/<逻辑名>.json`（取数结果）、`params.json`（参数取值）、`trigger.json`（触发时间、规则时区、全量或单条触发及单条触发的去重键）与 `feedback.json`（声明需要的反馈字段）；结果写入 `/output/result.json`。样例运行使用同一布局。

校验分两处：安装与发布时检查声明结构、入口在 `compute/` 中、依赖在执行镜像中（沿用依赖登记）、`data` 参数只引用 `params` 与触发信息、样例运行输出符合字段定义；保存主动任务时检查逻辑名绑定与工具标记（6.3）。

场景包只能由管理员安装发布（SP6），默认不进入 Skill 广场，Agent 加载时只作为方法使用，声明不生效。发布证据是平台用样例输入运行计算脚本的结果（退出码、输出字段校验、镜像摘要），与严格试运行分开；`SKILL.md` 的方法仍随 Agent 版本验证。

### 6.3 部署：扩展主动任务

不新增对象，在 `agent_routines` 上增加场景包部署：

| 字段 | 内容 |
| --- | --- |
| 场景包 | 从所固定 Agent Version 已选用的 Skill 中选择；版本随 Agent Version，不单独引用 |
| 数据工具绑定 | 每个逻辑名对应该 Agent Version 已选定 Connector 中的一个工具；工具须带“可供程序步骤调用”标记 |
| 参数取值 | 在声明的允许范围内设置，未设置的用默认值 |
| 接收范围 | 部门或员工列表；接收人字段映射出的员工必须落在范围内；按 SP4 (a) 运行时，持有该 Agent 可见角色的员工也须都在范围内 |
| 外部账号渠道 | 接收人字段用哪个渠道映射（如 `erp:<实例编码>`，SP3） |
| 放权阶段 | 影子运行、通知相关人（第一期只开放这两级）；影子运行时全部跟进项只交给规则负责人；切换时的处理见 6.9 |
| 规则负责人 | 沿用 `recipient_user_id`：影子运行的接收人、告警通知的接收人（6.12） |

日程、时区、Workspace 与输入模板沿用主动任务现有字段；规则时区同时用于数据新鲜度检查与计算中的“今天”。引用场景包的主动任务必须固定 Agent Version，不使用升级策略；更换 Agent Version 导致场景包版本变化时，规则自动回到影子运行，以新的运行证据重新进入下一级。修改部署字段与修改日程一样，只能在草稿或暂停状态进行，并清空确认的配置修订。员工本人的定时任务不提供这些字段。

### 6.4 触发与受理

`agent_routine_executions` 增加阶段与结果，受理规则修订如下（实施前写入功能规则第 7、8 节）：

```
受理（去重、重叠与名额、场景包状态、授权复核并冻结）
  → 取数 → 计算 → 条件 ─┬─ 不满足：no_work（记原因，结束）
                        └─ 满足：原子创建 Session/Task/Run → Agent → 交付 → delivered
失败：fetch_failed / compute_failed / agent_failed / delivery_failed（记原因，告警规则负责人）
进程中断：取数、计算、条件阶段收敛为 interrupted；Agent 阶段沿用 Run 的恢复；交付阶段记 delivery_failed
```

**状态的存储：**

- `admission_status` 保持 `accepted`、`skipped`、`interrupted` 三个取值不变，原因沿用 `reason_code`。
- 新增 `stage`，记录当前或最后所处的阶段：`fetch`、`compute`、`condition`、`agent`、`delivery`；未引用场景包的主动任务为空。
- 新增 `outcome`，记录结果：`no_work`、`fetch_failed`、`compute_failed`、`agent_failed`、`delivery_failed`、`delivered`；进行中为空。
- `accepted` 必须有 `task_id` 与 `run_id` 的约束改为：未引用场景包的触发照旧；引用场景包的触发在创建 Run 之后必须有，Run 未能创建的 `agent_failed` 除外。

**受理：**

- 顺序为：同一触发去重（沿用 `(routine_id, trigger_id)` 唯一键）→ 规则状态 → 重叠与待处理名额 → 场景包状态 → 执行身份与授权复核（与现有 `authorizeAgentRoutine` 同一规则）。全部通过后，把执行身份、授权上限、数据工具绑定与参数取值冻结到触发记录，再进入取数；任一项不通过都按现有方式记为 `skipped` 并写明原因，不取数。
- 场景包所在的 Skill 被停用或被标为“依赖缺失”时不予受理（原因“场景包不可用”），同时告警规则负责人，不降级继续。
- 重叠检查、按 Agent 与全局的待处理名额，都把 `stage` 处在取数、计算、条件且 `outcome` 为空的触发计入，与未结束的 Run 合并计算。
- 创建 Run 时按现行规则再复核一次授权。

**进程中断与启动恢复：** 启动恢复扫描 `stage` 处在取数、计算、条件且 `outcome` 为空的触发，按准备中断语义收敛为 `interrupted`，不续办、不补跑，名额随之释放。Agent 阶段沿用现有 Run 的恢复语义，Run 进入终态后由平台继续交付段。交付在一个数据库事务内完成对账、跟进项与通知的写入；中断时事务回滚，启动恢复记为 `delivery_failed` 并告警，第一期不自动重试。

**其他：**

- DSH 不可用时：取数、计算与条件可以完成，需要 Agent 的触发记为 `agent_failed`，跟进项不交付（不以程序结果冒充 Agent 结论，规范 AS-03）。Agent 段各种失败的分界见 6.8。
- 反馈要求立即重新取数时，作为一次新的手动触发（单条触发），只对该跟进项的去重键取数、计算与对账（6.9），经过同一受理、去重与重叠规则。

### 6.5 取数

- 新建服务端 MCP 客户端（Streamable HTTP，`tools/call`），复用 Connector 的加密凭据、生效清单摘要、健康与停用检查。
- 按受理时冻结的执行身份、授权上限与数据工具绑定调用；每次调用前再检查 Connector 状态与工具标记，不通过记 `fetch_failed`。
- 只调用绑定且带标记的工具；标记与 Tool 名称和输入 Schema 摘要绑定，Schema 变化后自动失效（规范 AS-05）。
- 各次调用只使用参数取值与触发信息，互不传递结果；单条触发时按声明的映射把去重键字段转为查询参数。
- **数据新鲜度：** 声明了刷新时间字段的查询，平台在取数结束后检查返回的刷新时间不早于声明的要求（如“规则时区的触发当日 0 点”）；不满足记 `fetch_failed`（原因“数据未刷新”）并告警，不进入计算。
- 每次调用设超时与返回大小上限；失败、超时、超限都记为取数失败，不当作“没有数据”。
- 每次调用写入与 DSH 调用同等的 Tool 级审计。

### 6.6 计算

- 经单独的 `ContainerExecutor` 实例（SP7）调用 `runPythonSandbox`，在一次性容器中运行声明的入口；隔离方式沿用成果解析的路径，目录按 6.2 的约定。
- 资源另设计算段档位：内存、CPU、单文件与输出合计大小、运行时长。现有 `runPythonSandbox` 的资源固定为 256 MB、0.5 CPU、单文件 10 MB，SP-S1 要让执行器支持按请求的档位设置，数值用欠料样例实测后定稿。
- 等槽位与运行分别计时：等槽位超过 10 分钟记 `compute_failed`（原因“排队超时”），运行超过档位时长记 `compute_failed`（原因“运行超时”）。
- 输入目录放本次取数结果、参数取值、触发信息与反馈字段（JSON 文件），输出目录收结果文件；运行结束后无论成败删除两个目录。
- **反馈字段输入：** 声明为“作为计算输入”的反馈字段，由平台从该规则未关闭跟进项的最新反馈中读出，按去重键写入 `feedback.json`，带录入人与录入时间；只读，审计记录条数与摘要。
- 输出按声明的字段校验；不合格记为计算失败。stdout 与 stderr 不保存正文。

### 6.7 条件

只提供固定判断方式：计数比较、布尔字段为真、字段存在。不在服务进程中解释表达式。条件不满足记 `no_work` 并写明原因；数据是否新鲜不由条件判断（6.5）。

### 6.8 Agent 段

- 条件成立后原子创建 Session/Task/Run（Workspace 与输入模板沿用主动任务），把声明选定的字段作为只读输入交给 AI 同事（每次最多条数按声明，紧急优先），按工具结果经过数据防护遮盖。
- **输出（结构化输出接通前的过渡做法）：** AI 同事按 `SKILL.md` 把结果写成 `output/` 下两份约定文件名的 CSV：说明（去重键、说明）与排序（去重键、候选编号、名次、一句理由）。现行成果登记接受 CSV、不接受 JSON，这两份文件因此登记为该 Run 的成果；交付段读取并按声明校验：去重键须在本次计算输出中，候选编号须来自该键的可行候选，数量与日期不取自 AI 输出。说明与排序只用于展示和决定显示顺序，不驱动任何动作（规范 1.1）。主动任务的 Run 若不适用现行成果登记，SP-S2 把它列入功能规则第 1 节的修订。结构化输出约束（AS-02、AS-10）接通后改用结构化结果。
- **失败与交付：**

| 情况 | 是否交付跟进项 | 记录 |
| --- | --- | --- |
| Run 未能创建（创建前的授权复核未通过）或派发中断 | 不交付 | `agent_failed`，写明原因，告警 |
| Run 失败、取消或超时（含 DSH 不可用、预算耗尽） | 不交付 | `agent_failed`，关联 Run，告警 |
| Run 成功，但输出文件缺失、格式不符或校验不通过 | 照常交付，不带说明与排序（SP9） | `delivered`，标注“AI 输出不合格”及原因 |

Run 没有成功结束，说明 Agent 段没有执行完，按 AS-03 不以程序结果冒充 Agent 结论；Run 已成功但输出不合格，只是说明的质量问题，事实与候选都来自程序。

### 6.9 跟进项

**归属与可见：** 跟进项属于工作规则，按接收人可见；规则负责人和具备该主动任务管理权限的管理员可以查看全部（入口见 6.11）。

**写权限：** 第一期只有当前接收人能执行反馈动作；规则负责人与管理员只读。影子运行时接收人就是规则负责人。

**对账（全量触发）：** 每次交付按去重键与该规则当前交付代次的未关闭跟进项比对：

| 情况 | 结果 |
| --- | --- |
| 新出现的键（含此前已自动关闭的键） | 新建，标“新增” |
| 已有的键，变差字段按声明的比较方式变差 | 更新事实，标“变差” |
| 已有的键，没有变差 | 更新事实，标“持续”，记录持续天数 |
| 已有的键，接收人字段映射到另一名员工 | 转给新接收人，状态与处理记录保留，对新接收人标“新增”并计入其通知；原接收人不再可见 |
| 已有未关闭的键本次没有出现 | 自动关闭，原因写“本次结果中不再出现” |
| 已因误报或“不再处理”关闭的键再次出现，重开字段没有变化 | 不新建，不通知 |
| 已因误报或“不再处理”关闭的键再次出现，重开字段按声明的比较方式变化 | 重新打开，标“变差” |

**单条触发：** 只取计算输出中该键的行，只对这一项对账；该键不再出现时只关闭这一项，不关闭其他键，也不新建其他键。

**放权阶段切换：** 规则记录当前交付代次，每次切换放权阶段加一；未关闭跟进项的去重键只在同一代次内唯一。

- **影子运行 → 通知相关人：** 关闭影子期全部未关闭跟进项（原因“放权阶段切换”），处理记录不继承；下一次运行全部按“新增”分发并通知。
- **通知相关人 → 影子运行**（含更换 Agent Version 后自动回退）：已分发的跟进项保留给原接收人，转为只读并标“规则回到影子运行”，停止对账与通知；它们仍算未关闭，反馈字段继续作为计算输入。新代次的结果只交给规则负责人。
- **再次进入通知相关人：** 关闭影子期的跟进项；下一次运行中，键与冻结项相同的新跟进项接续冻结项的状态、反馈字段与处理记录，按与冻结时的事实对比标“持续”或“变差”，冻结项关闭（原因“已由新结果接续”）；没有再出现的冻结项自动关闭。

**接收人：** 接收人字段经工作规则指定的外部账号渠道（SP3）映射到员工；映射不到或不在接收范围内的行不投递，记入运行记录，在规则详情中提示负责人并发告警通知（6.12）。接收人离职或被移出接收范围后不再看到原跟进项；这些项在规则详情中标为“无人负责”，外部账号对应更新后按“接收人变化”转交。

**规则暂停与停用：** 暂停期间跟进项照常可以反馈，需要重新取数的等恢复后的下一次运行。停用后未关闭跟进项转为只读并标“规则已停用”，接收人仍可查看；停用超过 30 天未恢复的，未关闭项自动关闭（原因“规则停用”）。所有跟进项关闭后按 SP5 保留 180 天。主动任务没有删除操作，不另设删除处理。

**状态：** 待处理 → 处理中 → 已关闭。关闭原因：自动关闭、误报、不再处理（如不再续签）、放权阶段切换、已由新结果接续、规则停用，以及动作声明的其他原因。

**数据：** 事实字段直接来自计算输出并记录来源与取数时间；AI 说明单独存放、单独展示。

### 6.10 员工端

- 入口按 SP1。列表按紧急程度、来源（AI 同事）或声明的分组字段（如供应商）分组；可按来源筛选、搜索；页签为待处理、处理中、已关闭。
- 详情按声明的字段类型通用渲染：紧急程度与理由、事实、日期对比、表格、AI 说明、候选方案（可行与不可行分开，标明核对结果）、处理记录、来源（规则、场景包版本、数据服务）。只读的跟进项（规则回到影子运行、规则已停用）显示原因，不显示反馈表单。
- 反馈动作按声明生成表单，只对当前接收人显示；结果按 6.9 更新状态，需要立即重新取数的按 6.4 处理。
- “问 {AI 同事}”打开员工与该 AI 同事的新对话，带入跟进项的快照作为只读上下文；数据可见范围按 SP4。
- 通知按 SP8，点击进入跟进项列表或对应详情。
- 页面成型后按 `AGENTS.md` 的 Spec → Code → Verify → Test → Green 流程补验收目录与 Playwright 用例。按 SP1 在主导航加入口时，同步修改 `AGENTS.md` 的主导航规则、功能规则第 2 节与项目空间方案第 12 节，更新 `e2e/catalog/`、`personal-workbench.spec.ts` 与 `collab-mode.spec.ts`，并跑完整的 `pnpm test:e2e`。

### 6.11 管理端

- **场景包：** Skill 详情中展示场景声明、计算入口、参数与发布证据（只读）。
- **数据服务：** MCP 连接器详情中逐个工具设置或撤销“可供程序步骤调用”标记，显示标记人、时间与是否因 Schema 变化失效。
- **主动任务：** 新增“场景包部署”分区（6.3）；运行记录按阶段展示取数、计算、条件、Agent 与交付的结果与原因，不展示业务数据正文；新增“跟进项”页签，规则负责人与管理员只读查看该规则的全部跟进项，可按状态、接收人筛选，并列出最近一次运行的未投递行与“无人负责”的项。
- **外部账号：** 组织架构中按 ERP 实例维护采购员代码对应，一名员工可有多个代码，支持 CSV 导入（SP3）。

### 6.12 权限、通知与审计

- 标记工具：需要 MCP 连接器管理权限。
- 发布场景包：需要 Skill 发布权限（SP6）。
- 配置部署：沿用主动任务管理权限。
- 反馈动作：只有当前接收人（6.9）。
- **通知种类：**
  - 跟进项通知（暂定 `follow_up_digest`，对象类型 `agent_routine`）：按 SP8 每人每次运行一条，只在有新增或变差时发送。
  - 主动任务告警（暂定 `agent_routine_alert`，对象类型 `agent_routine`）：发给规则负责人，覆盖阶段失败（`fetch_failed`、`compute_failed`、`agent_failed`、`delivery_failed`、中断）、因场景包不可用不予受理，以及有未投递行。读取时按负责人当前对该主动任务的权限解析；同一规则已有未读告警时合并，更新次数与最近一次原因（参照功能规则第 7 节的合并做法）。
  - 两个种类都要修改 `user_notifications` 的 `kind` 与 `object_type` 约束。
- **审计：** 工具调用；计算段的 Skill 版本摘要、入口、执行镜像摘要、退出码、等槽位与运行耗时、是否超限、输入与输出摘要（含反馈字段的条数）；条件结论；交付结果（新增、变差、转交、关闭条数，未投递行数）；放权阶段切换；反馈动作。审计不保存业务数据正文。

## 7. 欠料风险预警（首个场景）

### 7.1 业务背景

业务链为客户订单 → 物料统计 → 物料采购 → 欠料追踪 → 计划排产。采购员经常不能按期完成所需物料的采购到货。需要按计划排产日期倒推，定时找出有到货风险的物料，通知负责的采购员及时与供应商跟进，并给出可行的替代方案。

### 7.2 计算口径

- **需求：** `SUGGESTION_PLAN` 的建议计划行，已含 ERP 的最终计算结果。ERP 不保留历史，新增与变差靠跟进项对账（6.9）判断。
- **风险来源：** 建议计划行尚未转采购单；已下单，但对应采购单有到货风险。
- **最晚到货日** = 需求日（按订单交货日期倒推的排产日期）− 检验入库天数 − 安全缓冲。
- **预计到货日** 依次取：SRM 预计到货（发货单）› 供应商确认交期（SRM 中的确认与采购员录入取确认时间较晚的一个，SP2）› PO 承诺交期 › 今天 + 采购提前期（尚未下单时）。“今天”是规则时区的触发日期。
- **风险类型：** 未下单；交期未确认；确认交期晚于最晚到货日；应发未发；在途但晚到；数量不足；数据冲突（ERP 与 SRM 不一致）。
- **数量不足：** 最晚到货日之前预计能到的数量小于需求数量。能到的数量按已发货的取发货数量、未发货的取确认数量、未确认的取订购数量，采购员录入了可到数量时按 SP2 的同一规则取用。
- **紧急程度（阈值为参数）：** 紧急 = 预计晚到，且距最晚到货日不超过紧急阈值；重要 = 预计晚到但时间较多，或交期未确认、应发未发、数量不足，且距最晚到货日不超过重要阈值；关注 = 其余情况，含数据冲突。预计晚到且涉及重点客户订单时上调一级。
- **运输天数**（判断应发未发）按供应商近 6 个月发货到签收的中位数计算，数据与其他查询一轮取齐（7.3）。
- **接收人：** ERP 中该物料的采购员。
- **替代方案：** 只对预计晚到的风险计算，每类都核对能否赶上最晚到货日，不可行的也列出原因。
  - 分批催交：按需求日分段的缺口，算出首批最晚要多少、哪天前到；
  - 换或加供应商：货源清单中其他合格供应商，今天下单加提前期能否赶上，附价差与近 6 个月准时率；
  - 替代料：BOM 替代关系，可用量是否覆盖缺口且不挤占替代料自身的需求，需工艺或客户确认的标出；
  - 调拨：其他仓库或工厂未分配的可用库存与调拨天数。
- **反馈：** 已跟进（新交期、可到数量；两项作为计算输入，提交后立即对这一条重新取数）；采用方案（只能从可行候选中选，进入处理中，取数结果中出现对应采购单或调拨单后重算）；误报（原因必填：数据错误、已到货 ERP 未入账、需求已取消或变更、其他）。

### 7.6 上线与放权

- **平台改造之前：** 按规范 1.1 的现行约束，可以先做模型编排的影子运行：一条主动任务，欠料助手经 MCP 读取上述查询，接收人只有采购主管，结果留在该次 Task 中。用它尽早核对数据口径与查询，不作为交付给采购员的依据。
- **平台上线后：** 影子运行 2～4 周，跟进项只交给采购主管；对照实际到货校准参数。
- **进入“通知相关人”的条件：** 采购主管确认口径无误，且误报率连续 2 周低于约定值。切换时按 6.9 关闭影子期跟进项，下一次运行全部按新增分发。
- **衡量指标：** 预警覆盖率（实际晚到的物料中提前预警过的比例）、误报率、平均提前预警天数、替代方案采纳率。

## 9. 风险

| 风险 | 处理 |

| 外部账号对应维护不及时，跟进项发不出去 | 未投递行进入运行记录并告警规则负责人；数据服务提供核对查询 |

| ERP 刷新晚于运行时间，导致用旧数据 | 取数段按规则时区检查数据刷新时间，未刷新记取数失败并告警 |
| AI 说明与事实不一致 | 事实只取计算输出，AI 说明单独展示并注明仅供参考；候选编号校验 |
| 误报多，采购员不再看 | 影子运行校准；误报率作为进入下一级的门槛；误报原因用于修正口径 |
