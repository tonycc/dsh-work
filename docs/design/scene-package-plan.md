## 1. 背景与目标

企业里有一类反复出现的工作：按固定周期从业务系统取数，按确定的规则算出需要处理的事项，分给具体的人，并跟踪处理结果。欠料风险预警是第一个例子，来料检验异常、价格协议到期、应收逾期属于同一类。

现在的平台做这类工作有三个缺口：外部数据只能由模型调用 MCP 取得；每次触发都会创建 Run 并唤醒模型；结果停留在该次 Task 中，主动任务只有一个接收人。若为每个场景单独建业务应用，又无法复制，也用不上 Agent 的配置组合能力。

目标：

- **新场景只靠场景包和配置上线：** 写一个场景包（方法、计算脚本、场景声明），必要时在共享数据服务中增加查询，再配置一条主动任务。不新建服务，不新做页面。
- **程序做确定的事，模型做判断：** 取数、计算、条件判断与交付由平台程序执行；说明与方案排序由 AI 同事经 DSH 执行。
- **结果变成有人负责的跟进项：** 按人分发，与上一次结果对账，标出新增、变差与持续，接收反馈，处理完或不再出现时关闭。
- **欠料风险预警作为首个场景走通，**分期见第 10 节。

## 2. 已确认事项（2026-11-10）

| 事项 | 内容 |

| 方向 | 不按场景建业务应用。一个场景 = 场景包（Skill）+ 共享数据服务中的查询 + 一条主动任务（部署）；固定步骤由程序编排（规范 1.1，PR #113） |

## 3. 已确认决策（2026-11-10）

以下决策均按“确认的做法”一列拍板，可选做法保留作记录。SP2、SP3、SP4、SP7 在同日评审后调整，原做法写在该行。

| 编号 | 决策 | 可选做法 | 确认的做法 |
| --- | --- | --- | --- |
| SP1 | 员工端跟进项的入口 | (a) A、B 两种模式主导航各加“跟进项”，只在本人有跟进项或在某条规则的接收范围内时显示；(b) 不加导航，从头像菜单与通知进入；(c) A 模式“新对话”首页上方显示今日跟进项摘要，点开进入列表 | (a)。跟进项是每天要看的工作清单，放进头像菜单太深；只对相关的人显示（规则负责人也显示，6.10），不影响其他员工。主导航“固定入口”的规则要同步修改：`AGENTS.md` 浏览器 E2E 一节、功能规则第 2 节与项目空间方案第 12 节 |
| SP2 | 采购员录入的交期在预计到货日来源中的位置 | (a) 等同“供应商确认”：排在 SRM 预计到货之后、PO 承诺之前，之后 SRM 出现新的预计到货时以 SRM 为准；(b) 优先于全部来源，直到采购员撤销 | (a)。SRM 发货数据比口头答复更可靠；采购员录入只填补 SRM 还没有数据的空档。**评审后补充：** 原方案中录入的交期没有进入计算的通道；现由平台按去重键保存声明的反馈值，作为计算的只读输入（6.6），不随跟进项关闭而失效；录入的交期与 SRM 中的供应商确认交期取确认时间较晚的一个 |
| SP3 | ERP 采购员代码与员工账号的对应 | (a) 复用 `external_account_bindings` 增加 ERP 渠道，管理员在组织架构中维护（支持 CSV 导入）；(b) 新建专用对应表 | (a)，**评审后补充三条约束**（原做法只写“新增 `channel = 'erp'`”）：渠道按 ERP 实例区分（`erp:<实例编码>`，工作规则写明用哪个渠道映射接收人字段），多套 ERP 的代码重复时互不冲突；ERP 渠道允许一名员工有多个代码（“每人每渠道一个有效绑定”的唯一约束只保留给钉钉），代码在渠道内仍唯一；ERP 绑定在账号停用（与 `invalidateUserBindings` 同一事务）和钉钉离职检查确认离职（与 `invalidateDeparted` 同一事务）时失效，没有钉钉绑定的员工只能等账号停用；重置密码、钉钉解绑不影响它（`invalidateUserBindings` 现在只处理钉钉，且在重置密码与解绑时也会调用，不能直接扩大它的范围）。现有读取绑定的代码都按 `channel` 过滤或按绑定 ID 读取，实施时放宽 `channel` 的 check 约束。数据服务可另提供“采购员代码—工号”查询用于核对，但不自动绑定 |
| SP4 | “问 AI”时的数据可见范围（MCP 不带员工身份） | (a) 第一期接受：数据服务不按人过滤，设计记录写明过滤层为“无”及理由；(b) 先由平台为每次执行向 MCP 传递员工身份（参照模型网关的 Attempt 令牌，另立项）；(c) 第一期不提供“问 AI” | 欠料场景选 (a)：采购数据在采购部内部本就互相可见。涉及敏感数据的场景按 (b) 或 (c)。**评审后补充：** 谁能与该 AI 同事对话由 Agent 的可见角色决定，“问 AI”按钮本身不构成数据边界（原做法只写“问 AI 只对接收范围内的员工开放”）。因此以“引用该 Agent 的全部未停用（草稿、启用、暂停）SP4 (a) 规则的接收范围并集”为边界，规则暂停修改部署时边界不消失；这些规则全部停用后，复核仍按停用时的接收范围执行，要放开须由管理员在该 Agent 上明确解除（记审计）：员工以该 Agent 发起任何 Run（对话、本人定时任务、项目空间中的 @ 与任务）时，在统一的执行授权处按当前组织架构复核，不在并集内的拒绝，已开始的会话在下一次发起 Run 时同样复核；保存工作规则或修改该 Agent 的可见角色时，列出持有可见角色但不在并集内的员工作为提示（他们将不能使用该 Agent）。设计记录写明数据边界是这条运行时复核 |
| SP5 | 保留期 | 跟进项关闭后保留时长；取数结果与计算输出的保留时长 | 跟进项关闭后保留 180 天；取数结果与计算输出只存交付与审计所需字段，保留 30 天，触发记录中的阶段、原因与摘要照常保留；通知沿用 NC4 的 90 天。规则停用后的处理见 6.9 |
| SP6 | 谁能发布场景包 | (a) 只有具备 Skill 发布权限的管理员在管理端安装发布；(b) 员工经 Skill 创建专家起草、管理员审核后发布 | (a)。`skill_draft_save` 拒绝含场景声明的包。场景包含会被平台执行的声明与脚本，第一期不开放员工起草 |
| SP7 | 计算段的并发 | (a) 与成果解析共用执行器槽位，排队超时记为“计算失败”；(b) 为计算段单独建执行器实例与槽位 | (b)，**评审后调整**（原选 (a)，并误写成“共用 4 个槽位”）。成果解析用的是单独的 `ContainerExecutor` 实例，只有 2 个槽位（`main.ts`），而且它的 60 秒超时包含等槽位的时间；计算一次最长要占几分钟，共用会让员工上传文件后的成果解析超时失败。新建一个实例的代码成本低。计算段实例默认 2 个槽位；等槽位超过 10 分钟记为“计算失败”（原因“排队超时”），与运行超时分开记录。处在取数、计算阶段的触发计入主动任务的重叠检查与待处理名额（6.4），不占用 Worker 与后台车道 |
| SP8 | 跟进项通知的合并方式 | (a) 每人每次运行合并为一条（标题写紧急条数，正文写新增与变差条数），只在有新增或变差时发送；(b) 新增紧急项另发一条 | (a)。按 NC1 只收与本人相关的事件，按 NC6 不为“无变化”发通知 |
| SP9 | AI 同事输出不合格时 | (a) 跟进项照常交付，不带说明与排序，运行记录标注原因；(b) 整次交付失败 | (a)。事实与候选方案来自程序，AI 说明缺失不影响跟进项的正确性。只适用于 Run 已成功结束的情况；Run 未能创建或失败时不交付，分界见 6.8 |

## 4. 边界

- 不建设通用工作流引擎：固定“取数 → 计算 → 条件判断 → Agent 执行 → 交付”五段，每段只执行一次，没有任意分支、循环或多 Agent 编排（规范 1.1）。Agent 段只在两种情况下不执行：条件不满足时的关闭对账与反馈触发的单条运行，都不创建 Run、不调用模型（6.4）。
- 不写外部业务系统：程序步骤只调用标记为“可供程序步骤调用”的只读工具；对外部系统的写操作只在 DSH 中经授权执行，且真实 Agent 审批固定为 `never`，第一期不开放。
- 第一期只在管理员配置的 Agent 主动任务中提供；员工本人的定时任务不支持场景包。
- 不新增钉钉推送；钉钉工作通知随[钉钉接入方案](dingtalk-integration-plan.md) DT-S2 另行规划。
- 欠料二期事项（供应商协同、联动排产、挪用其他订单库存）不在本文范围。

## 5. 现状与缺口

| 能力 | 现状 | 缺口 |
| --- | --- | --- |
| 主动任务 | `agent_routines` 固定 `agent_version_id`、Workspace、日程与时区、输入模板、单个 `recipient_user_id`、岗位角色与数据范围上限；状态只有草稿、启用、暂停、停用，停用是终态（不能再启用），没有删除；列表、详情、执行记录与手动触发都只对平台管理员开放，负责人只在员工端看到自己收到的结果（`recipientResults`）；触发类型只有 `scheduled`、`manual`、`event`、`missed`；创建 Task 时数据库触发器要求规则为启用状态。`agent_routine_executions` 的 `admission_status` 只有 `accepted`、`skipped`、`interrupted`，`accepted` 必须同时有 `task_id` 与 `run_id`。受理顺序是先检查重叠与待处理名额，再复核授权，紧接着创建 Run；重叠、名额与准备中断恢复都经 `run_id` 关联 `runs` 表计数 | 没有场景包部署字段；没有取数、计算、条件阶段，也没有“无事可做”“取数失败”“计算失败”“Agent 段失败”等结果；Run 之前的阶段不计入名额与恢复；授权复核紧挨着创建 Run，取数前没有复核；没有反馈触发类型；业务员工担任负责人时看不到规则与告警 |
| 平台调用 MCP | 服务端只做连接检查（经 DSH 读取工具目录，不调用模型）与认证 `ping`，没有 `tools/call` 客户端 | 新建服务端 MCP 客户端；新增“可供程序步骤调用”标记（规范 AS-05） |
| 一次性容器 | `ContainerExecutor.runPythonSandbox` 已用于成果解析：独立实例 2 个槽位；断网一次性容器，场景包、输入、输出分别挂载为 `/skill`（只读、工作目录）、`/input`（只读）、`/output`；资源固定为 256 MB 内存、0.5 CPU、单文件 10 MB；时长由调用方传入，成果解析为 60 秒，且包含等槽位的时间 | 计算段单独的执行器实例；执行器支持按请求的档位设置资源、单文件与输出上限，等槽位与运行分别计时；输入输出校验、样例运行与审计字段 |
| Skill 包 | 安装与提交时解析 `SKILL.md` frontmatter、工具与 Python 依赖；包内有 `.py` 即装配 `python_execute`，多文件包装配 `read` | 识别场景声明；计算脚本不装配 `python_execute`；场景包不进入 Skill 广场；新的发布证据 |
| 成果登记 | 运行结束后登记 `output/` 顶层普通文件，接受 Markdown、纯文本、CSV、HTML、Office、PDF 与图片，不接受 JSON（功能规则第 1 节） | 过渡期 Agent 输出用 CSV 成果承载（6.8）；主动任务的 Run 是否适用同一登记规则在 SP-S2 核对 |
| 站内通知 | `user_notifications`，按 `kind` 区分，现有任务指派、任务完成、@ 我、定时任务失败（`automation_failed`，只按员工定时任务的所有者解析）等；`kind` 与 `object_type` 有 check 约束（最近一次在 0118 修改）；Agent 主动任务没有任何失败通知 | 新增跟进项通知与主动任务告警两个种类，修改约束（SP8、6.12） |

| 数据防护 | 员工消息、定时任务与主动任务的输入模板会做密钥预检；工具结果只遮盖 | 取数结果与计算输出发给模型前按工具结果遮盖（规范 1.1） |
| 跟进项 | 无（Agent 数据平面已于 2026-10-16 删除） | 新的平台对象，见 6.9 |

## 6. 方案

### 6.1 总体结构

```
场景包（Skill，管理员发布）           共享数据服务（只读 MCP Server，按业务系统建设）
  SKILL.md   给 AI 同事的方法             erp：建议计划、采购单、货源清单与库存……
  compute/   计算脚本                     srm：确认交期、发货与到货、供应商表现……
  scene.yaml 场景声明
         │ 被 Agent Version 选用                    │ 由 Connector 登记，工具逐个标记
         ▼                                          ▼
主动任务（部署）：固定 Agent Version · 逻辑名绑定 · 参数 · 接收范围 · 放权阶段 · 日程
         │ 触发
         ▼
受理（授权复核并冻结）→ 取数（MCP 客户端）→ 计算（一次性容器）→ 条件 →（满足）Run/Attempt → DSH → 交付
                                                                   （不满足）关闭对账
                                                                                      │
                                                     跟进项（对账、按人分发、通知、反馈、问 AI）
```

### 6.2 场景包格式

场景包是普通 Skill 包加两样东西：

```
SKILL.md          给模型的方法（frontmatter 照旧）
scene.yaml        场景声明，平台读取
compute/          计算脚本与样例输入；不登记为模型可调用的入口
  risk.py
  samples/        样例输入与期望的输出字段
```

`scene.yaml` 的内容（字段名在 SP-S1 定稿）：

| 部分 | 内容 |
| --- | --- |
| `data` | 用到的数据工具逻辑名与查询参数，如 `erp.suggestion_plan_open`；参数只能引用 `params` 与触发信息，不能引用其他查询或计算的结果；每个查询的数据刷新时间字段与新鲜度要求（6.5）；去重键字段到查询参数的映射（单条重新取数时使用）。不写 Connector ID、地址或凭据 |
| `compute` | 入口（`compute/` 下登记的单个 `.py` 文件）、需要读取的反馈值、输出字段定义、样例输入位置 |
| `condition` | 从平台固定的判断方式中选择，只引用输出字段，如“风险行数大于 0” |
| `agent` | 交给 AI 同事的字段子集、每次最多条数与排序依据、输出文件的约定（6.8） |
| `follow_up` | 跟进项模板：标题、事实字段及类型（文本、数量、日期、日期对比、表格、候选方案）、分组字段；去重键；接收人字段；判定变差的字段与比较方式；误报或“不再处理”后重新打开所依据的字段与比较方式 |
| `actions` | 反馈动作：类型（填写字段、选择候选、带原因关闭）、字段、结果状态、是否立即重新取数（单条触发）、字段是否作为计算输入及其失效条件 |
| `params` | 可调参数的名称、类型、默认值与允许范围 |

**计算脚本的目录约定：** 沿用一次性容器的固定挂载，与 `python_execute` 经环境变量给出路径的约定不同。`/skill` 是场景包目录（只读、工作目录）；`/input` 下有 `fetch/<逻辑名>.json`（取数结果）、`params.json`（参数取值）、`trigger.json`（触发时间、规则时区、全量或单条触发及单条触发的去重键）与 `feedback.json`（声明需要的有效反馈值）；结果写入 `/output/result.json`。样例运行使用同一布局。

**单文件入口：** 第一期计算入口必须是单个文件，不能导入 `compute/` 下的其他模块。执行镜像为 Python 3.12，`python -I` 同时去掉脚本所在目录与当前目录（`-m` 方式也一样），并忽略 `PYTHONPATH`，同目录的辅助模块无法导入。需要拆分模块时，另行评审由平台提供固定的启动器设置导入路径。

校验分两处：安装与发布时检查声明结构、入口在 `compute/` 中、依赖在执行镜像中（沿用依赖登记）、`data` 参数只引用 `params` 与触发信息、样例运行输出符合字段定义；保存主动任务时检查逻辑名绑定与工具标记（6.3）。

场景包只能由管理员安装发布（SP6），默认不进入 Skill 广场，Agent 加载时只作为方法使用，声明不生效。发布证据是平台用样例输入运行计算脚本的结果（退出码、输出字段校验、镜像摘要），与严格试运行分开；`SKILL.md` 的方法仍随 Agent 版本验证。

### 6.3 部署：扩展主动任务

不新增对象，在 `agent_routines` 上增加场景包部署：

| 字段 | 内容 |
| --- | --- |
| 场景包 | 从所固定 Agent Version 已选用的 Skill 中选择；版本随 Agent Version，不单独引用 |
| 数据工具绑定 | 每个逻辑名对应该 Agent Version 已选定 Connector 中的一个工具；工具须带“可供程序步骤调用”标记 |
| 参数取值 | 在声明的允许范围内设置，未设置的用默认值 |
| 接收范围 | 部门或员工列表；接收人字段映射出的员工必须落在范围内；按 SP4 (a) 运行时，它同时是该 Agent 可用人员的边界（SP4） |
| 外部账号渠道 | 接收人字段用哪个渠道映射（如 `erp:<实例编码>`，SP3） |
| 放权阶段 | 影子运行、通知相关人（第一期只开放这两级）；影子运行时全部跟进项只交给规则负责人；切换时的处理见 6.9 |
| 规则负责人 | 沿用 `recipient_user_id`：影子运行的接收人、告警通知的接收人（6.12），在员工端的负责人视图查看该规则（6.10） |

日程、时区、Workspace 与输入模板沿用主动任务现有字段；规则时区同时用于数据新鲜度检查与计算中的“今天”。引用场景包的主动任务必须固定 Agent Version，不使用升级策略；更换 Agent Version 导致场景包版本变化时，规则自动回到影子运行，以新的运行证据重新进入下一级。修改部署字段与修改日程一样，只能在草稿或暂停状态进行，并清空确认的配置修订。停用是终态，停用时按 6.9 关闭全部未关闭跟进项。员工本人的定时任务不提供这些字段。

### 6.4 触发与受理

`agent_routine_executions` 增加阶段与结果，受理规则修订如下（实施前写入功能规则第 7、8 节）：

```
全量触发：受理（去重、规则状态、重叠与名额、场景包状态、授权复核并冻结）
  → 取数 → 计算 → 条件 ─┬─ 满足：原子创建 Session/Task/Run → Agent → 交付 → delivered
                        └─ 不满足：有未关闭跟进项时做关闭对账 → no_work
单条触发（反馈）：受理 → 取数 → 计算 → 只对该键对账（不执行 Agent 段）→ delivered
失败：fetch_failed / compute_failed / agent_failed / delivery_failed（记原因，告警规则负责人）
规则不再启用：在下一个阶段开始前收敛为 skipped（routine_inactive），不告警
进程中断：取数、计算、条件阶段收敛为 interrupted；Run 已结束而交付未完成的按 6.8 的分界处理
```

**触发类型：**

- 全量触发沿用现有的 `scheduled`、`manual`、`event`、`missed`。
- 新增 `feedback`（单条触发）：接收人提交要求立即重新取数的反馈动作后，由平台以系统身份发起，不要求平台管理员权限（反馈动作本身按 6.9 的写权限校验）。`trigger_id` 由“跟进项 ID + 反馈事件 ID”生成，重复提交不会产生第二次触发。`kind` 的 check 约束增加 `feedback`。

**状态的存储：**

- `admission_status` 保持 `accepted`、`skipped`、`interrupted` 三个取值不变，原因沿用 `reason_code`。
- 新增 `stage`，记录当前或最后所处的阶段：`fetch`、`compute`、`condition`、`agent`、`delivery`；未引用场景包的主动任务为空。
- 新增 `outcome`：进行中为空；结束时取 `no_work`、`fetch_failed`、`compute_failed`、`agent_failed`、`delivery_failed`、`delivered`，或与 `admission_status` 一致的 `skipped`、`interrupted`。引用场景包的触发只有进行中时 `outcome` 为空。
- 新增 `delivery_mode`：`full`（经过 Agent 段的全量交付）、`close_only`（条件不满足时的关闭对账）、`single`（单条触发）；新增 `delivery_attempts`（交付尝试次数）。
- `accepted` 的约束（拟议，SP-S2 定稿）改为满足以下之一：
  - 未引用场景包（`stage` 为空），且有 `task_id` 与 `run_id`，与现行一致；
  - `stage` 为 `fetch`、`compute`、`condition`；
  - `stage` 为 `agent`，且有 `run_id`，或 `outcome = 'agent_failed'` 且 `reason_code = 'run_not_created'`；
  - `stage` 为 `delivery`，且有 `run_id`，或 `delivery_mode` 为 `close_only`、`single`。

**受理：**

- 全量触发的顺序为：同一触发去重（沿用 `(routine_id, trigger_id)` 唯一键）→ 规则状态 → 重叠与待处理名额 → 场景包状态 → 执行身份与授权复核（与现有 `authorizeAgentRoutine` 同一规则）。全部通过后，把执行身份、授权上限、数据工具绑定与参数取值冻结到触发记录，再进入取数；任一项不通过都记为 `skipped` 并写明原因，不取数。
- 场景包所在的 Skill 被停用或被标为“依赖缺失”时不予受理（原因“场景包不可用”），同时告警规则负责人，不降级继续。
- 引用场景包的全量触发，重叠检查与按 Agent、全局的待处理名额都按“`kind` 不是 `feedback`、`admission_status = 'accepted'` 且 `outcome` 为空”计入，覆盖 Run 之前的阶段和“Run 已结束、交付未完成”的记录；未引用场景包的触发照旧按 Run 状态计入。
- 单条触发不参与全量触发的重叠判断，也不被全量触发阻挡。同一跟进项同时只有一次单条触发，10 分钟内最多受理一次；期间的反馈照常保存为有效反馈值（6.6），由下一次运行使用。单条触发不创建 Run，不计入待处理名额（按 Agent 与全局），计算使用同一个计算段执行器实例。
- 创建 Run 时按现行规则再复核一次授权。

**规则状态的检查：** 取数、计算、条件、创建 Run 与交付开始前都检查规则状态。规则已暂停或停用时收敛为 `skipped`（原因 `routine_inactive`），不告警。数据库触发器要求创建 Task 时规则为启用状态，这一检查保证正常情况下不会走到触发器报错；并发下仍报错时同样记 `skipped`（`routine_inactive`）。暂停时按功能规则第 7 节清理没有 Attempt 的 Run，对应触发也记 `skipped`（`routine_inactive`），不记 `agent_failed`。

**交付的一致性：** 交付按规则加锁串行；对账结果、跟进项、通知与 `outcome = 'delivered'` 在同一个数据库事务内写入，提交即完成，中断时整体回滚、不留部分结果。跟进项现有事实的取数时间晚于本次触发时，本次不覆盖这一项（只记入运行记录），避免较早的触发晚交付时把事实改回旧值或误关新出现的项。

**进程中断与启动恢复：**

- `stage` 处在取数、计算、条件且 `outcome` 为空的触发，按准备中断语义收敛为 `interrupted`，不续办、不补跑，名额随之释放。
- Agent 阶段沿用现有 Run 的恢复语义。派发中断时，引用场景包的触发记 `outcome = 'agent_failed'`（原因 `dispatch_interrupted`），`admission_status` 保持 `accepted`；现有 `recoverInterruptedPreparations` 把派发中断写成 `interrupted`，对引用场景包的触发要分开处理。
- `stage = 'agent'`、`admission_status = 'accepted'`、`outcome` 为空、Run 已到终态的触发，按 6.8 的分界处理：Run 成功则进入交付段，Run 失败或取消记 `agent_failed`。
- 每次交付（含关闭对账与单条触发）开始前，先单独提交 `stage = 'delivery'` 与 `delivery_attempts` 加一，之后只按交付的次数上限处理。启动时 `stage = 'delivery'` 且 `outcome` 为空的触发，尝试次数少于 2 次的重新执行一次，达到 2 次的记 `delivery_failed` 并告警。

**DSH 不可用时：** 取数、计算与条件可以完成，需要 Agent 的全量触发记为 `agent_failed`，跟进项不交付（不以程序结果冒充 Agent 结论，规范 AS-03）；关闭对账与单条触发不需要 Agent，照常执行。Agent 段各种失败的分界见 6.8。

### 6.5 取数

- 新建服务端 MCP 客户端（Streamable HTTP，`tools/call`），复用 Connector 的加密凭据、生效清单摘要、健康与停用检查。
- 按受理时冻结的执行身份、授权上限与数据工具绑定调用；每次调用前再检查 Connector 状态与工具标记，不通过记 `fetch_failed`。
- 只调用绑定且带标记的工具；标记与 Tool 名称和输入 Schema 摘要绑定，Schema 变化后自动失效（规范 AS-05）。
- 各次调用只使用参数取值与触发信息，互不传递结果。单条触发时按声明的映射把去重键字段转为查询参数（如物料编码）；这时取到的数据只够更新该项的事实与结论，不够重算候选方案（6.9）。
- **数据新鲜度：** 声明了刷新时间字段的查询，平台在取数结束后检查返回的刷新时间不早于声明的要求（如“规则时区的触发当日 0 点”）；不满足记 `fetch_failed`（原因“数据未刷新”）并告警，不进入计算。
- 每次调用设超时与返回大小上限；失败、超时、超限都记为取数失败，不当作“没有数据”。
- 每次调用写入与 DSH 调用同等的 Tool 级审计。

### 6.6 计算

- 经单独的 `ContainerExecutor` 实例（SP7）调用 `runPythonSandbox`，在一次性容器中运行声明的入口；隔离方式沿用成果解析的路径，目录与单文件入口按 6.2 的约定。
- 资源另设计算段档位：内存、CPU、单文件与输出合计大小、运行时长。现有 `runPythonSandbox` 的资源固定为 256 MB、0.5 CPU、单文件 10 MB，SP-S1 要让执行器支持按请求的档位设置，数值用欠料样例实测后定稿。
- 等槽位与运行分别计时：等槽位超过 10 分钟记 `compute_failed`（原因“排队超时”），运行超过档位时长记 `compute_failed`（原因“运行超时”）。
- 输入目录放本次取数结果、参数取值、触发信息与有效反馈值（JSON 文件），输出目录收结果文件；运行结束后无论成败删除两个目录。
- **有效反馈值：** 声明为“作为计算输入”的反馈字段，平台按（规则、去重键、字段）单独保存为有效反馈值，不随跟进项关闭而失效。例如录入的交期使风险消除、跟进项自动关闭后，下一次运行仍读到这个交期，同一风险不会作为“新增”重新出现。有效反馈值按动作声明的失效条件过期（从平台固定的方式中选择，如“所录入的日期过后”）；同一键再次录入时以最后一次为准；影子运行切换到通知相关人时，清除影子代次录入的有效反馈值（6.9）。平台把有效反馈值写入 `feedback.json`，带录入人与录入时间；只读，审计记录条数与摘要。
- 输出按声明的字段校验；不合格记为计算失败。stdout 与 stderr 不保存正文。

### 6.7 条件

只提供固定判断方式：计数比较、布尔字段为真、字段存在。不在服务进程中解释表达式。数据是否新鲜不由条件判断（6.5）。

条件不满足时记 `no_work` 并写明原因。该规则仍有未关闭跟进项时，平台执行关闭对账（`delivery_mode = 'close_only'`）：按 6.9 关闭本次结果中不再出现的项（风险全部消除时即全部关闭），不新建、不更新其他项、不发通知，不创建 Run、不调用模型（规范 1.1 原则 4）。单条触发没有条件段，按 6.9 只对该键对账。

### 6.8 Agent 段

- 全量触发条件成立后，原子创建 Session/Task/Run（Workspace 与输入模板沿用主动任务），把声明选定的字段作为只读输入交给 AI 同事（每次最多条数按声明，紧急优先），按工具结果经过数据防护遮盖。
- **输出（结构化输出接通前的过渡做法）：** AI 同事按 `SKILL.md` 把结果写成 `output/` 下两份约定文件名的 CSV：说明（去重键、说明）与排序（去重键、候选编号、名次、一句理由）。现行成果登记接受 CSV、不接受 JSON，这两份文件因此登记为该 Run 的成果；交付段读取并按声明校验：去重键须在本次计算输出中，候选编号须来自该键的可行候选，数量与日期不取自 AI 输出。说明与排序只用于展示和决定显示顺序，不驱动任何动作（规范 1.1）。主动任务的 Run 若不适用现行成果登记，SP-S2 把它列入功能规则第 1 节的修订。结构化输出约束（AS-02、AS-10）接通后改用结构化结果。
- **不执行 Agent 段的两种情况：** 关闭对账与单条触发（规范 1.1“固定形态”）。单条触发更新事实后，跟进项保留上一次的 AI 说明与排序，并标注“说明基于 {时间} 的运行”，由下一次全量运行更新。
- **失败与交付：**

| 情况 | 是否交付跟进项 | 记录 |
| --- | --- | --- |
| Run 未能创建（创建前的授权复核未通过）或派发中断 | 不交付 | `agent_failed`，写明原因（`run_not_created` 或 `dispatch_interrupted`），告警 |
| Run 失败、取消或超时（含 DSH 不可用、预算耗尽） | 不交付 | `agent_failed`，关联 Run，告警 |
| Run 成功，但输出文件缺失、格式不符或校验不通过 | 照常交付，不带说明与排序（SP9） | `delivered`，标注“AI 输出不合格”及原因 |

Run 没有成功结束，说明 Agent 段没有执行完，按 AS-03 不以程序结果冒充 Agent 结论；Run 已成功但输出不合格，只是说明的质量问题，事实与候选都来自程序。规则暂停或停用导致的 Run 未能创建或被清理，按 6.4 记 `skipped`，不属于本表。

### 6.9 跟进项

**归属与可见：** 跟进项属于工作规则，按接收人可见；规则负责人和具备该主动任务管理权限的管理员可以查看全部（负责人在员工端的负责人视图，6.10；管理员在管理端，6.11）。

**写权限：** 第一期只有当前接收人能执行反馈动作；规则负责人与管理员只读。影子运行时接收人就是规则负责人。

**对账（全量触发）：** 每次交付按去重键与该规则当前交付代次的未关闭跟进项比对：

| 情况 | 结果 |
| --- | --- |
| 新出现的键（含此前已自动关闭的键） | 新建，标“新增” |
| 已有的键，变差字段按声明的比较方式变差 | 更新事实，标“变差” |
| 已有的键，没有变差 | 更新事实，标“持续”，记录持续天数 |
| 已有的键，接收人字段映射到另一名员工 | 转给新接收人，状态与处理记录保留，对新接收人标“新增”并计入其通知；原接收人不再可见 |
| 已有未关闭的键本次没有出现 | 自动关闭，原因写“本次结果中不再出现” |
| 被接收人标为误报或“不再处理”的键再次出现，重开字段没有变化 | 不新建，不通知 |
| 被接收人标为误报或“不再处理”的键再次出现，重开字段按声明的比较方式变化 | 重新打开，标“变差” |

误报与“不再处理”的抑制按（规则、去重键）查找接收人关闭的跟进项，跨交付代次有效，随该项按 SP5 的保留期清理而结束；影子期由规则负责人标的误报只用于校准，不带入通知阶段。

**单条触发：** 只取计算输出中该键的行，只对这一项对账：更新事实、风险结论与紧急程度；不更新候选方案（候选的可行性取决于其他物料的需求与同一批库存，按物料过滤取数时算不准，候选标注“来自 {时间} 的全量运行”），也不改动 AI 说明。该键不再出现时只关闭这一项；不关闭、不新建其他键；不发通知（发起人就是接收人，结果在详情中直接显示）。

**放权阶段切换：** 规则记录当前交付代次，每次切换放权阶段加一；未关闭跟进项的去重键只在同一代次内唯一。

- **影子运行 → 通知相关人：** 关闭影子期全部未关闭跟进项（原因“放权阶段切换”），处理记录、影子期的误报与影子代次录入的有效反馈值都不带入（负责人为校准录入的交期不能抵消采购员的风险）；下一次运行全部按“新增”分发并通知。
- **通知相关人 → 影子运行**（含更换 Agent Version 后自动回退）：已分发的跟进项保留给原接收人，转为只读并标“规则回到影子运行”，停止对账与通知；有效反馈值按键保存，不受影响。新代次的结果只交给规则负责人。冻结超过 30 天仍未再次放权的，冻结项自动关闭（原因“回到影子运行超时”）。
- **再次进入通知相关人：** 关闭影子期的跟进项；下一次运行中，键与冻结项相同的新跟进项接续冻结项的状态与处理记录，按与冻结时的事实对比标“持续”或“变差”，冻结项关闭（原因“已由新结果接续”）；没有再出现的冻结项自动关闭。

**接收人：** 接收人字段经工作规则指定的外部账号渠道（SP3）映射到员工；映射不到或不在接收范围内的行不投递，记入运行记录，在负责人视图中提示（6.10）并发告警通知（6.12）。接收人离职或被移出接收范围后不再看到原跟进项；这些项在负责人视图中标为“无人负责”，外部账号对应更新后按“接收人变化”转交。

**规则暂停与停用：** 暂停期间跟进项照常可以反馈；要求重新取数的反馈仍保存为有效反馈值，对应的单条触发记 `skipped`（`routine_inactive`），由恢复后的下一次运行使用。停用是终态（现有代码不能从停用恢复为启用）：停用时关闭全部未关闭跟进项，冻结项一并关闭（原因“规则停用”），接收人仍可在“已关闭”页签查看。所有跟进项关闭后按 SP5 保留 180 天。主动任务没有删除操作，不另设删除处理。

**状态：** 待处理 → 处理中 → 已关闭。关闭原因：自动关闭、误报、不再处理（如不再续签）、放权阶段切换、已由新结果接续、回到影子运行超时、规则停用，以及动作声明的其他原因。

**数据：** 事实字段直接来自计算输出并记录来源与取数时间；候选方案与 AI 说明记录来自哪次全量运行；AI 说明单独存放、单独展示。

## 7. 欠料风险预警（首个场景）

### 7.1 业务背景

业务链为客户订单 → 物料统计 → 物料采购 → 欠料追踪 → 计划排产。采购员经常不能按期完成所需物料的采购到货。需要按计划排产日期倒推，定时找出有到货风险的物料，通知负责的采购员及时与供应商跟进，并给出可行的替代方案。

### 7.2 计算口径

- **需求：** `SUGGESTION_PLAN` 的建议计划行，已含 ERP 的最终计算结果。ERP 不保留历史，新增与变差靠跟进项对账（6.9）判断。
- **风险来源：** 建议计划行尚未转采购单；已下单，但对应采购单有到货风险。
- **最晚到货日** = 需求日（按订单交货日期倒推的排产日期）− 检验入库天数 − 安全缓冲。
- **预计到货日** 依次取：SRM 预计到货（发货单）› 供应商确认交期（SRM 中的确认与采购员录入取确认时间较晚的一个，SP2）› PO 承诺交期 › 今天 + 采购提前期（尚未下单时）。“今天”是规则时区的触发日期。
- **风险类型：** 未下单；交期未确认；确认交期晚于最晚到货日；应发未发；在途但晚到；数量不足；数据冲突（ERP 与 SRM 不一致）。
- **数量不足：** 最晚到货日之前预计能到的数量小于需求数量。能到的数量按已发货的取发货数量、未发货的取确认数量、未确认的取订购数量，采购员录入了可到数量时按 SP2 的同一规则取用。
- **紧急程度（阈值为参数）：** 紧急 = 预计晚到，且距最晚到货日不超过紧急阈值；重要 = 预计晚到但时间较多，或交期未确认、应发未发、数量不足，且距最晚到货日不超过重要阈值；关注 = 其余情况，含数据冲突。预计晚到且涉及重点客户订单时上调一级。
- **运输天数**（判断应发未发）按供应商近 6 个月发货到签收的中位数计算，数据与其他查询一轮取齐（7.3）。
- **接收人：** ERP 中该物料的采购员。
- **替代方案：** 只对预计晚到的风险计算，每类都核对能否赶上最晚到货日，不可行的也列出原因。
  - 分批催交：按需求日分段的缺口，算出首批最晚要多少、哪天前到；
  - 换或加供应商：货源清单中其他合格供应商，今天下单加提前期能否赶上，附价差与近 6 个月准时率；
  - 替代料：BOM 替代关系，可用量是否覆盖缺口且不挤占替代料自身的需求，需工艺或客户确认的标出；
  - 调拨：其他仓库或工厂未分配的可用库存与调拨天数。
- **反馈：** 已跟进（新交期、可到数量；两项按去重键保存为有效反馈值，所录入的交期过后失效；提交后对这一条发起单条触发）；采用方案（只能从可行候选中选，进入处理中，取数结果中出现对应采购单或调拨单后重算）；误报（原因必填：数据错误、已到货 ERP 未入账、需求已取消或变更、其他）。

### 7.6 上线与放权

- **平台改造之前：** 按规范 1.1 的现行约束，可以先做模型编排的影子运行：一条主动任务，欠料助手经 MCP 读取上述查询，接收人只有采购主管，结果留在该次 Task 中。用它尽早核对数据口径与查询，不作为交付给采购员的依据。
- **平台上线后：** 影子运行 2～4 周，跟进项只交给采购主管；对照实际到货校准参数。
- **进入“通知相关人”的条件：** 采购主管确认口径无误，且误报率连续 2 周低于约定值。切换时按 6.9 关闭影子期跟进项，下一次运行全部按新增分发。
- **衡量指标：** 预警覆盖率（实际晚到的物料中提前预警过的比例）、误报率、平均提前预警天数、替代方案采纳率。

## 9. 风险

| 风险 | 处理 |
| --- | --- |
| 场景声明不断加功能，演变成工作流引擎 | 固定五段与固定判断方式；新增声明能力须有实际场景并经评审 |
| 通用渲染满足不了个别场景的展示 | 字段类型按场景需要逐个加入（如日期对比），不允许场景自带页面代码 |
| 计算脚本是租户代码 | 一次性断网容器、依赖只来自执行镜像、输出按字段校验、只由管理员发布 |
| 计算数据量超出档位 | 档位按样例实测定稿；超出时把候选计算下推到数据服务 |
| 数据服务不按人过滤 | 交付由程序按接收人拆分；SP4 在发起 Run 时按接收范围复核；敏感场景先解决身份传递 |
| 单条触发与全量运行的结果不一致 | 单条触发只更新事实与结论，不更新候选与 AI 说明，并标注来源；下一次全量运行统一更新 |
| 外部账号对应维护不及时，跟进项发不出去 | 未投递行进入运行记录并告警规则负责人；数据服务提供核对查询 |
| 去重键不稳定，跟进项每天都变成新增 | 去重键用稳定的业务标识，不含采购单号；欠料-0 请客户 IT 确认行号与需求序号的稳定性 |
| ERP 刷新晚于运行时间，导致用旧数据 | 取数段按规则时区检查数据刷新时间，未刷新记取数失败并告警 |
| AI 说明与事实不一致 | 事实只取计算输出，AI 说明单独展示并注明仅供参考；候选编号校验 |
| 误报多，采购员不再看 | 影子运行校准；误报率作为进入下一级的门槛；误报原因用于修正口径 |

**P1 清单：**

- **不唤醒模型（AS-03）：** 条件不满足、取数失败、计算失败、关闭对账与单条触发的路径上不创建 Run，模型网关与 DSH 的请求数为 0；`no_work`、`fetch_failed`、`compute_failed`、`agent_failed` 四种记录可区分；DSH 不可用时全量触发记 `agent_failed`，单条触发照常完成。
- **受理与状态：** 受理时授权复核未通过不取数；Skill 停用或依赖缺失时不予受理并告警；取数中暂停规则，触发收敛为 `skipped` 且不告警；单条触发进行中时定时全量运行不被跳过，同一项 10 分钟内重复反馈只受理一次。
- **恢复与交付：** 取数或计算中重启后收敛为 `interrupted` 且名额释放；Run 成功后、交付前重启，启动后交付一次且不重复生成跟进项与通知；Run 失败后重启记 `agent_failed`、不交付；交付中断后最多重试一次；派发中断记 `agent_failed`；较早的触发晚交付时不覆盖较新的事实。
- **取数与计算：** 标记因 Schema 变化失效后取数失败；数据未刷新记取数失败；计算排队超时与运行超时分开记录；计算容器断网且输入输出目录用后删除。
- **跟进项：** 同一键连续两次运行标“持续”、数据变差标“变差”、消失后自动关闭；风险全部消除时关闭对账关闭全部未关闭项；单条反馈消除风险后该项被关闭、其他键不受影响；录入的交期消除风险后连续两次运行都不重新出现“新增”；误报后重开字段变化才重新打开，误报抑制跨代次；更换 Agent Version 后回到影子运行，已分发项转为只读、再次放权后接续；规则停用时未关闭项全部关闭；影子运行只交给规则负责人。
- **通知与权限：** 通知按人合并、告警按规则合并；采购员能打开跟进项通知（不依赖主动任务的查看权限）；非管理员的规则负责人能看到告警与负责人视图；授权复核未通过的跳过与停机错过会告警；ERP 绑定在重置密码后仍有效，账号停用或钉钉离职确认后失效；不在接收范围内的员工不能经对话、本人定时任务或项目空间使用该 Agent

Mock 或 P1 通过不能代替 P2；未完成 P2 前，总览须标注场景包与跟进项“未真实验收”。
