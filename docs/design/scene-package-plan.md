## 1. 背景与目标

企业里有一类反复出现的工作：按固定周期从业务系统取数，按确定的规则算出需要处理的事项，分给具体的人，并跟踪处理结果。欠料风险预警是第一个例子，来料检验异常、价格协议到期、应收逾期属于同一类。

现在的平台做这类工作有三个缺口：外部数据只能由模型调用 MCP 取得；每次触发都会创建 Run 并唤醒模型；结果停留在该次 Task 中，主动任务只有一个接收人。若为每个场景单独建业务应用，又无法复制，也用不上 Agent 的配置组合能力。

目标：

- **新场景只靠场景包和配置上线：** 写一个场景包（方法、计算脚本、场景声明），必要时在共享数据服务中增加查询，再配置一条主动任务。不新建服务，不新做页面。
- **程序做确定的事，模型做判断：** 取数、计算、条件判断与交付由平台程序执行；说明与方案排序由 AI 同事经 DSH 执行。
- **结果变成有人负责的跟进项：** 按人分发，与上一次结果对账，标出新增、变差与持续，接收反馈，处理完或不再出现时关闭。
- **欠料风险预警作为首个场景走通，**分期见第 10 节。

## 2. 已确认事项（2026-11-10）

| 事项 | 内容 |
| --- | --- |
| 方向 | 不按场景建业务应用。一个场景 = 场景包（Skill）+ 共享数据服务中的查询 + 一条主动任务（部署）；固定步骤由程序编排（规范 1.1，PR #113） |
| 名称 | 按人交付、可反馈的对象叫“跟进项”，不与项目任务的“待办”状态混用 |
| 欠料一期范围 | 预警采购员；替代方案四类（分批催交、换或加供应商、替代料、调拨），挪用其他订单的库存放二期；采购员反馈必须做（误报、已跟进录入新交期、采用方案）；只用站内通知；与供应商协同（SRM 交期确认请求）、联动排产放二期 |
| 欠料数据口径 | 按订单交货日期倒推排产；ERP `SUGGESTION_PLAN` 表已有最终计算结果，每天刷新一次、不保留历史；ERP 中每个物料有对应采购员；ERP 有货源清单、BOM 替代关系与多仓可用库存；ERP 与 SRM 都提供 API；计算参数需要维护 |

## 3. 已确认决策（2026-11-10）

以下决策均按“确认的做法”一列拍板，可选做法保留作记录。

| 编号 | 决策 | 可选做法 | 确认的做法 |
| --- | --- | --- | --- |
| SP1 | 员工端跟进项的入口 | (a) A、B 两种模式主导航各加“跟进项”，只在本人有跟进项或在某条规则的接收范围内时显示；(b) 不加导航，从头像菜单与通知进入；(c) A 模式“新对话”首页上方显示今日跟进项摘要，点开进入列表 | (a)。跟进项是每天要看的工作清单，放进头像菜单太深；只对相关的人显示，不影响其他员工。主导航固定入口的规则（`AGENTS.md`）要同步修改 |
| SP2 | 采购员录入的交期在预计到货日来源中的位置 | (a) 等同“供应商确认”：排在 SRM 预计到货之后、PO 承诺之前，之后 SRM 出现新的预计到货时以 SRM 为准；(b) 优先于全部来源，直到采购员撤销 | (a)。SRM 发货数据比口头答复更可靠；采购员录入只填补 SRM 还没有数据的空档 |
| SP3 | ERP 采购员代码与员工账号的对应 | (a) 复用 `external_account_bindings`，新增 `channel = 'erp'`，管理员在组织架构中维护（支持 CSV 导入）；(b) 新建专用对应表 | (a)。现有读取钉钉绑定的查询抽查均已按 `channel` 过滤；实施时须逐一核对，并放宽 `channel` 的 check 约束。数据服务可另提供“采购员代码—工号”查询用于核对，但不自动绑定 |
| SP4 | “问 AI”时的数据可见范围（MCP 不带员工身份） | (a) 第一期接受：数据服务不按人过滤，“问 AI”只对该规则接收范围内的员工开放，设计记录写明过滤层为“无”及理由；(b) 先由平台为每次执行向 MCP 传递员工身份（参照模型网关的 Attempt 令牌，另立项）；(c) 第一期不提供“问 AI” | 欠料场景选 (a)：采购数据在采购部内部本就互相可见。涉及敏感数据的场景按 (b) 或 (c) |
| SP5 | 保留期 | 跟进项关闭后保留时长；取数结果与计算输出的保留时长 | 跟进项关闭后保留 180 天；取数结果与计算输出只存交付与审计所需字段，保留 30 天，触发记录中的阶段、原因与摘要照常保留；通知沿用 NC4 的 90 天 |
| SP6 | 谁能发布场景包 | (a) 只有具备 Skill 发布权限的管理员在管理端安装发布；(b) 员工经 Skill 创建专家起草、管理员审核后发布 | (a)。`skill_draft_save` 拒绝含场景声明的包。场景包含会被平台执行的声明与脚本，第一期不开放员工起草 |
| SP7 | 计算段的并发 | (a) 与成果解析共用执行器的 4 个容器槽位，排队超时记为“计算失败”；(b) 为计算段单独配置槽位 | (a)。巡检一天几次，量小；排队超时默认 10 分钟。另按规范 1.1，处在取数、计算阶段的触发计入后台车道名额 |
| SP8 | 跟进项通知的合并方式 | (a) 每人每次运行合并为一条（标题写紧急条数，正文写新增与变差条数），只在有新增或变差时发送；(b) 新增紧急项另发一条 | (a)。按 NC1 只收与本人相关的事件，按 NC6 不为“无变化”发通知 |
| SP9 | AI 同事输出不合格时 | (a) 跟进项照常交付，不带说明与排序，运行记录标注原因；(b) 整次交付失败 | (a)。事实与候选方案来自程序，AI 说明缺失不影响跟进项的正确性。结构化输出约束（AS-02）接通前，排序只决定显示顺序 |

## 4. 边界

- 不建设通用工作流引擎：固定“取数 → 计算 → 条件判断 → Agent 执行 → 交付”五段，没有任意分支、循环或多 Agent 编排（规范 1.1）。
- 不写外部业务系统：程序步骤只调用标记为“可供程序步骤调用”的只读工具；对外部系统的写操作只在 DSH 中经授权执行，且真实 Agent 审批固定为 `never`，第一期不开放。
- 第一期只在管理员配置的 Agent 主动任务中提供；员工本人的定时任务不支持场景包。
- 不新增钉钉推送；钉钉工作通知随[钉钉接入方案](dingtalk-integration-plan.md) DT-S2 另行规划。
- 欠料二期事项（供应商协同、联动排产、挪用其他订单库存）不在本文范围。

## 5. 现状与缺口

| 能力 | 现状 | 缺口 |
| --- | --- | --- |
| 主动任务 | `agent_routines` 固定 `agent_version_id`、日程、输入模板、单个 `recipient_user_id`、岗位角色与数据范围上限；`agent_routine_executions` 的 `admission_status` 只有 `accepted`、`skipped`、`interrupted`，`accepted` 必须同时有 `task_id` 与 `run_id` | 没有场景包部署字段；受理即创建 Run，没有取数、计算、条件阶段，也没有“条件不满足”“取数失败”“计算失败”的状态 |
| 平台调用 MCP | 服务端只做连接检查（经 DSH 读取工具目录，不调用模型）与认证 `ping`，没有 `tools/call` 客户端 | 新建服务端 MCP 客户端；新增“可供程序步骤调用”标记（规范 AS-05） |
| 一次性容器 | `ContainerExecutor.runPythonSandbox` 已用于成果解析：断网一次性容器，入参为 Skill 目录、输入目录、输出目录与入口，最多 4 个槽位 | 计算段复用这条路径，补输入输出校验、样例运行与审计字段 |
| Skill 包 | 安装与提交时解析 `SKILL.md` frontmatter、工具与 Python 依赖；包内有 `.py` 即装配 `python_execute`，多文件包装配 `read` | 识别场景声明；计算脚本不装配 `python_execute`；场景包不进入 Skill 广场；新的发布证据 |
| 站内通知 | `user_notifications`，按 `kind` 区分，现有任务指派、任务完成、@ 我、定时任务失败等 | 新增跟进项通知种类（SP8） |
| 外部账号 | `external_account_bindings` 只有 `channel = 'dingtalk'`，每人每渠道一个有效绑定，外部 ID 在渠道内唯一 | 新增 `erp` 渠道（SP3）与维护界面 |
| 数据防护 | 员工消息、定时任务与主动任务的输入模板会做密钥预检；工具结果只遮盖 | 取数结果与计算输出发给模型前按工具结果遮盖（规范 1.1） |
| 跟进项 | 无（Agent 数据平面已于 2026-10-16 删除） | 新的平台对象，见 6.9 |

## 6. 方案

### 6.1 总体结构

```
场景包（Skill，管理员发布）           共享数据服务（只读 MCP Server，按业务系统建设）
  SKILL.md   给 AI 同事的方法             erp：建议计划、采购单、货源清单与库存……
  compute/   计算脚本                     srm：确认交期、发货与到货、供应商表现……
  scene.yaml 场景声明
         │ 被 Agent Version 选用                    │ 由 Connector 登记，工具逐个标记
         ▼                                          ▼
主动任务（部署）：固定 Agent Version · 逻辑名绑定 · 参数 · 接收范围 · 放权阶段 · 日程
         │ 触发
         ▼
取数（MCP 客户端）→ 计算（一次性容器）→ 条件 →（需要时）Run/Attempt → DSH → 交付
                                                                      │
                                     跟进项（对账、按人分发、通知、反馈、问 AI）
```

### 6.2 场景包格式

场景包是普通 Skill 包加两样东西：

```
SKILL.md          给模型的方法（frontmatter 照旧）
scene.yaml        场景声明，平台读取
compute/          计算脚本与样例输入；不登记为模型可调用的入口
  risk.py
  samples/        样例输入与期望的输出字段
```

`scene.yaml` 的内容（字段名在 SP-S1 定稿）：

| 部分 | 内容 |
| --- | --- |
| `data` | 用到的数据工具逻辑名与查询参数，如 `erp.suggestion_plan_open`；不写 Connector ID、地址或凭据 |
| `compute` | 入口（`compute/` 下登记的 `.py`）、输出字段定义、样例输入位置 |
| `condition` | 从平台固定的判断方式中选择，只引用输出字段，如“行数大于 0”“`data_refreshed_today` 为真” |
| `agent` | 交给 AI 同事的字段子集、每次最多条数与排序依据、要求的输出格式（每条说明、候选排序） |
| `follow_up` | 跟进项模板：标题、事实字段及类型（文本、数量、日期、日期对比、表格、候选方案）、分组字段；去重键；接收人字段；判定变差的字段与比较方式 |
| `actions` | 反馈动作：类型（填写字段、选择候选、带原因关闭）、字段、结果状态、是否立即重新取数 |
| `params` | 可调参数的名称、类型、默认值与允许范围 |

校验分两处：安装与发布时检查声明结构、入口在 `compute/` 中、依赖在执行镜像中（沿用依赖登记）、样例运行输出符合字段定义；保存主动任务时检查逻辑名绑定与工具标记（6.3）。

场景包只能由管理员安装发布（SP6），默认不进入 Skill 广场，Agent 加载时只作为方法使用，声明不生效。发布证据是平台用样例输入运行计算脚本的结果（退出码、输出字段校验、镜像摘要），与严格试运行分开；`SKILL.md` 的方法仍随 Agent 版本验证。

### 6.3 部署：扩展主动任务

不新增对象，在 `agent_routines` 上增加场景包部署：

| 字段 | 内容 |
| --- | --- |
| 场景包 | 从所固定 Agent Version 已选用的 Skill 中选择；版本随 Agent Version，不单独引用 |
| 数据工具绑定 | 每个逻辑名对应该 Agent Version 已选定 Connector 中的一个工具；工具须带“可供程序步骤调用”标记 |
| 参数取值 | 在声明的允许范围内设置，未设置的用默认值 |
| 接收范围 | 部门或员工列表；接收人字段映射出的员工必须落在范围内 |
| 放权阶段 | 影子运行、通知相关人（第一期只开放这两级）；影子运行时全部跟进项只交给规则负责人 |
| 规则负责人 | 沿用 `recipient_user_id`，影子运行的接收人、失败告警的接收人 |

引用场景包的主动任务必须固定 Agent Version，不使用升级策略；更换 Agent Version 导致场景包版本变化时，规则自动回到影子运行，以新的运行证据重新进入下一级。修改部署字段与修改日程一样，只能在草稿或暂停状态进行，并清空确认的配置修订。员工本人的定时任务不提供这些字段。

### 6.4 触发与受理

`agent_routine_executions` 增加阶段，受理规则修订如下（实施前写入功能规则第 7、8 节）：

```
受理 → 取数中 → 计算中 → 条件判断 ─┬─ 不满足：no_work（记原因，结束）
                                    └─ 满足：原子创建 Session/Task/Run → Agent 执行 → 交付 → 完成
任一阶段失败：fetch_failed / compute_failed / delivery_failed（记原因，告警规则负责人）
进程中断：按准备中断语义收敛为 interrupted，不续办、不补跑
```

- 去重沿用 `(routine_id, trigger_id)` 唯一键；重叠检查把处在取数、计算、条件阶段的触发与未结束的 Run 一起计入。
- 放宽 `accepted` 必须有 `task_id` 的约束：只有进入 Agent 执行后才有 Task 与 Run。
- 场景包不需要 Agent 执行（声明省略 `agent`）时，条件满足后直接交付。
- 场景包所在的 Skill 被停用或被标为“依赖缺失”时，触发记为失败，不降级继续。
- DSH 不可用时：取数、计算与条件可以完成，需要 Agent 的触发记为失败，跟进项不交付（不以程序结果冒充 Agent 结论，规范 AS-03）。
- 反馈要求立即重新取数时，作为一次新的手动触发，只对该跟进项的去重键取数与计算，经过同一受理、去重与重叠规则。

### 6.5 取数

- 新建服务端 MCP 客户端（Streamable HTTP，`tools/call`），复用 Connector 的加密凭据、生效清单摘要、健康与停用复核。
- 只调用绑定且带标记的工具；标记与 Tool 名称和输入 Schema 摘要绑定，Schema 变化后自动失效（规范 AS-05）。
- 每次调用设超时与返回大小上限；失败、超时、超限都记为取数失败，不当作“没有数据”。
- 每次调用写入与 DSH 调用同等的 Tool 级审计。

### 6.6 计算

- 经 `ContainerExecutor.runPythonSandbox` 在一次性容器中运行声明的入口；容器姿态、资源上限与清扫同 `python_execute`（规范 1.1）。
- 输入目录放本次取数结果与参数取值（JSON 文件），输出目录收结果文件；运行结束后无论成败删除两个目录。
- 输出按声明的字段校验；不合格记为计算失败。stdout 与 stderr 不保存正文。
- 槽位与排队按 SP7。

### 6.7 条件

只提供固定判断方式：计数比较、布尔字段为真、字段存在。不在服务进程中解释表达式。

### 6.8 Agent 段

- 创建 Run 时把声明选定的字段作为只读输入交给 AI 同事（每次最多条数按声明，紧急优先），按工具结果经过数据防护遮盖。
- 输出要求为每条跟进项一段说明，以及对候选方案的排序与一句理由；平台解析后校验候选编号必须来自计算输出，数量与日期不取自 AI 输出。
- 解析失败或校验不通过按 SP9 处理。

### 6.9 跟进项

**归属与可见：** 跟进项属于工作规则，按接收人可见；规则负责人和具备该主动任务管理权限的管理员可以查看全部。接收人离职或被移出接收范围后不再看到，规则停用后已有跟进项保持只读、不再更新。

**对账：** 每次交付按去重键与该规则现有的未关闭跟进项比对：

| 情况 | 结果 |
| --- | --- |
| 新出现的键 | 新建，标“新增” |
| 已有的键，变差字段按声明的比较方式变差 | 更新事实，标“变差” |
| 已有的键，没有变差 | 更新事实，标“持续”，记录持续天数 |
| 已有未关闭的键本次没有出现 | 自动关闭，原因写“本次结果中不再出现” |
| 已标误报的键再次出现，且声明的关键字段明显变化 | 重新打开，标“变差” |

**接收人：** 接收人字段经外部账号对应（SP3）映射到员工；映射不到或不在接收范围内的行不投递，记入运行记录，并在规则详情中提示负责人。

**状态：** 待处理 → 处理中 → 已关闭。关闭原因：自动关闭、误报、不再处理（如不再续签），以及动作声明的其他原因。

**数据：** 事实字段直接来自计算输出并记录来源与取数时间；AI 说明单独存放、单独展示。

## 7. 欠料风险预警（首个场景）

### 7.1 业务背景

业务链为客户订单 → 物料统计 → 物料采购 → 欠料追踪 → 计划排产。采购员经常不能按期完成所需物料的采购到货。需要按计划排产日期倒推，定时找出有到货风险的物料，通知负责的采购员及时与供应商跟进，并给出可行的替代方案。

### 7.2 计算口径

- **需求：** `SUGGESTION_PLAN` 的建议计划行，已含 ERP 的最终计算结果。ERP 不保留历史，新增与变差靠跟进项对账（6.9）判断。
- **风险来源：** 建议计划行尚未转采购单；已下单，但对应采购单有到货风险。
- **最晚到货日** = 需求日（按订单交货日期倒推的排产日期）− 检验入库天数 − 安全缓冲。
- **预计到货日** 依次取：SRM 预计到货（发货单）› 供应商确认交期（采购员录入的位置按 SP2）› PO 承诺交期 › 今天 + 采购提前期（尚未下单时）。
- **风险类型：** 未下单；交期未确认；确认交期晚于最晚到货日；应发未发；在途但晚到；数量不足；数据冲突（ERP 与 SRM 不一致）。
- **紧急程度（阈值为参数）：** 紧急 = 预计晚到，且距最晚到货日不超过紧急阈值；重要 = 预计晚到但时间较多，或交期未确认、应发未发、数量不足，且距最晚到货日不超过重要阈值；关注 = 其余情况，含数据冲突。预计晚到且涉及重点客户订单时上调一级。
- **运输天数**（判断应发未发）按供应商近 6 个月发货到签收的中位数计算。
- **接收人：** ERP 中该物料的采购员。
- **替代方案：** 只对预计晚到的风险计算，每类都核对能否赶上最晚到货日，不可行的也列出原因。
  - 分批催交：按需求日分段的缺口，算出首批最晚要多少、哪天前到；
  - 换或加供应商：货源清单中其他合格供应商，今天下单加提前期能否赶上，附价差与近 6 个月准时率；
  - 替代料：BOM 替代关系，可用量是否覆盖缺口且不挤占替代料自身的需求，需工艺或客户确认的标出；
  - 调拨：其他仓库或工厂未分配的可用库存与调拨天数。
- **反馈：** 已跟进（新交期、可到数量，提交后立即重新取这一条）；采用方案（只能从可行候选中选，进入处理中，取数结果中出现对应采购单或调拨单后重算）；误报（原因必填：数据错误、已到货 ERP 未入账、需求已取消或变更、其他）。

### 7.6 上线与放权

- **平台改造之前：** 按规范 1.1 的现行约束，可以先做模型编排的影子运行：一条主动任务，欠料助手经 MCP 读取上述查询，接收人只有采购主管，结果留在该次 Task 中。用它尽早核对数据口径与查询，不作为交付给采购员的依据。
- **平台上线后：** 影子运行 2～4 周，跟进项只交给采购主管；对照实际到货校准参数。
- **进入“通知相关人”的条件：** 采购主管确认口径无误，且误报率连续 2 周低于约定值。
- **衡量指标：** 预警覆盖率（实际晚到的物料中提前预警过的比例）、误报率、平均提前预警天数、替代方案采纳率。

## 9. 风险

| 风险 | 处理 |
| --- | --- |
| 场景声明不断加功能，演变成工作流引擎 | 固定五段与固定判断方式；新增声明能力须有实际场景并经评审 |

| 外部账号对应维护不及时，跟进项发不出去 | 未投递行进入运行记录并提示规则负责人；数据服务提供核对查询 |

| AI 说明与事实不一致 | 事实只取计算输出，AI 说明单独展示并注明仅供参考；候选编号校验 |
| 误报多，采购员不再看 | 影子运行校准；误报率作为进入下一级的门槛；误报原因用于修正口径 |
