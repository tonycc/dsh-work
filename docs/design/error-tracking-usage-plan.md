## 1. 背景与目标

上线后需要回答两类问题：

1. **员工在怎么用：** 谁在用、用得多不多、用哪些 AI 同事和功能、哪些部门和员工没用起来、运行成功率如何。
2. **员工遇到了什么问题：** 员工看到的报错、白屏、加载失败、运行失败都能被记下来，按同一个问题归并，能从员工报给管理员的“链路编号”一路查到服务端失败与对应的运行。

目标：不引入外部监控服务、不采集对话内容，在管理端用两个页面分别看使用情况（“运行治理”分组）与错误记录（“安全与运维”分组）。

## 2. 边界

- **不引入第三方监控服务。** 不接 Sentry/GlitchTip、PostHog、Loki 等（OB1）；错误与访问事件写入平台自己的 PostgreSQL。
- **不采集内容。** 不记录对话正文、附件、请求体、查询参数、页面上的文字；错误消息在服务端统一脱敏（6.3）。管理员看不到消息正文的原则不变。员工主动反馈（OB15）时自己填写的说明除外。
- **不做告警（OB3）。** 管理员主动打开页面查看；告警留到二期，届时复用钉钉通知。
- **不做问题处理流程。** 第一期没有“已处理/指派/重新出现”状态，只有归并与统计。
- **不做性能监控。** 页面加载耗时、接口耗时、首字时间不在本期；“慢”不按错误记录（第 7 节）。
- **不复制运行失败。** 运行失败已记在 `run_attempts.error_code` 与 `run_events`，页面直接读取、按 `trace_id`/`run_id` 关联，不再写入新表。
- **不涉及 Agent 执行链路。** 本方案只是平台可观测性，不改 DSH 与 Runtime Adapter（AGENTS.md“Agent 执行统一使用 DSH”）。

## 4. 现状

**业务事件已经较全，且都在 PostgreSQL：**

| 内容 | 表 | 管理端页面 |
| --- | --- | --- |
| 运行与失败 | `runs`、`run_attempts`（`error_code`）、`run_events`（`run.failed`、`trace_id`） | 运营概览、Session 列表、Runtimes |
| 工具与外部调用 | `tool_audit_logs`、`mcp_invocation_audits`、`data_protection_gateway_events` | 审计、调用对账、数据防护 |
| 模型用量 | `model_usage_events` | 模型用量 |
| 管理操作与权限 | `audit_events` | 审计 |
| 会话活跃 | `sessions.last_active_at` | Session 列表 |
| 项目空间活动 | `workspace_activity_events`、`project_task_events` | 项目空间时间线 |

**缺口：**

1. **浏览器端错误完全收不到。** 员工端与管理端都没有 `app.config.errorHandler`，也没有监听 `window` 的 `error`、`unhandledrejection`；页面白屏、组件渲染失败、接口失败只出现在员工浏览器里（钉钉 H5 就是员工端，更看不到）。
2. **员工看到的失败提示没有记录。** 员工端经 `notifyActionFailure` 统一展示失败提示，管理端各页面以 `el-alert` 展示；这些只在界面上出现。
3. **服务端失败只写 stderr。** `server/src/http/http-error-log.ts` 的 `logHttpFailure` 输出一行脱敏 JSON（`event: http.request.failed`、`traceId`、路由模板、状态码、错误码）；500 响应已带 `traceId`，提示员工“将链路编号提供给管理员”，但管理员只能在服务器上翻 `server.stderr.log`，没有界面可查。
4. **进程级异常没有处理器。** 服务端没有 `uncaughtException`、`unhandledRejection` 处理，异常时只有 Node 默认输出。
5. **没有使用情况页面。** “运营概览”（`AdminOverviewView`）展示近 7 日运行数、最近 100 条运行状态、需关注事项与最近审计，是**当前状态**；没有按周期的活跃、功能使用、部门与个人分布。
6. **没有员工反馈入口。** 员工端回答上没有反馈或报告问题的操作，库中也没有对应表。
7. **版本号：** 管理端构建注入了 `__DSH_WORK_RELEASE_VERSION__`，员工端没有；两端构建都未生成源码映射。

## 5. 风险

| 风险 | 处理 |
| --- | --- |
| 错误消息或堆栈带出敏感值（密钥、个人信息、网址中的参数） | 服务端统一脱敏，不信任客户端（6.3）；只记路由名或路由模板，不记完整网址与查询参数；不记请求体与页面文字 |
| 上报接口被刷（尤其未登录可上报时） | 单次请求体上限、单条字段长度上限、按用户/IP 限流、同指纹短时间内只累加次数（6.2） |
| 报错风暴拖垮数据库 | 浏览器每次页面加载最多上报 20 条、同指纹去重；服务端写入异步、失败只写 stderr，不影响原响应 |
| 实时流断线重连造成噪声 | 员工端 SSE `onerror` 自动重连不上报，只有放弃重连时上报一条 |
| 按人明细涉及员工隐私 | 只展示使用量与功能分布，不展示对话标题与内容；页面只对有 `ops` 查看权限的管理员可见 |
| 源码映射泄露源码 | 映射文件不进入前端静态目录，只随 Release 存放在服务端，接口不提供下载（OB7） |

## 6. 方案

### 6.1 数据

迁移 `0133_error_tracking_usage`：

- **`error_groups`**：按指纹归并的问题。`tenant_id`、`fingerprint`、`source`（`workbench`、`admin`、`server`、`process`、`feedback`）、`kind`（`render`、`script`、`promise`、`api`、`notice`、`load`、`stream`、`http`、`uncaught`、`report`）、`message`（脱敏后首行，≤1,024 字符）、`first_seen_at`、`last_seen_at`、`occurrence_count`、`last_release`。唯一键 `(tenant_id, fingerprint)`。
- **`error_occurrences`**：每次发生的样本。`group_id`、`occurred_at`、`user_id`（未登录为空）、`release`、`route`（前端路由名或服务端路由模板）、`trace_id`、`run_id`、`client`（浏览器与系统的简称，如“钉钉 iOS”“Chrome 131 / macOS”，不存完整 UA）、`stack`（原始堆栈，脱敏后 ≤8,192 字符）、`note`（仅员工反馈，员工自己填写，≤500 字符）、`repeat_count`。
- **`product_events`**（OB8）：`tenant_id`、`user_id`、`app`（`workbench`/`admin`）、`page`（路由名）、`occurred_at`。同一员工同一页面 30 分钟内只记一次。
- 清理（OB10）：沿用服务端每 6 小时的清扫定时器，错误样本 90 天、页面访问 180 天；没有样本的 `error_groups` 一并删除。

### 6.2 采集与归并

**浏览器（员工端、管理端各一份，放在共享包中）：**

- 捕获点：
  - `app.config.errorHandler`（组件渲染）、`window` 的 `error`（含捕获阶段的资源加载失败）与 `unhandledrejection`；
  - `api/client.ts` 中的 `ApiError`：5xx、超时与网络失败，带上响应里的 `traceId`；
  - 失败提示（OB12）：员工端 `notifyActionFailure`、管理端页面错误提示的公共入口，记为 `notice`，带错误码与 `traceId`，不记提示原文以外的页面内容；
  - 白屏与分片失效（OB13）：`index.html` 内联脚本（不依赖应用打包代码）与 `vite:preloadError`，记为 `load`；
  - SSE 放弃重连时报一条。
- 上报：批量发送到 `POST /api/client-errors`，页面隐藏或关闭时用 `navigator.sendBeacon`；同一页面加载内同指纹只报一次并计数，每次加载最多 20 条。上报本身失败直接丢弃，不重试、不再触发上报。
- 员工端构建也注入版本号（与管理端相同的 `__DSH_WORK_RELEASE_VERSION__`）。
- 页面访问（OB8）：路由 `afterEach` 记录路由名，与错误一同批量发送。

**服务端：**

- `logHttpFailure` 在写 stderr 之外，异步写入错误表（`source: server`、`kind: http`），只记 5xx；写库失败只写 stderr，不影响已发出的响应。
- 新增 `uncaughtException`、`unhandledRejection` 处理：同步写 stderr，尽力在 2 秒内写库，然后保持 Node 现有行为（进程退出，由部署的守护进程拉起）。

**接口 `POST /api/client-errors`：**

- 请求体 ≤32 KB，每批 ≤20 条；已登录按用户每分钟 60 条，未登录（OB6）按来源 IP 每分钟 10 条，超出直接丢弃并返回 202。
- 指纹在服务端计算：`source` + `kind` + 规范化消息（去掉数字、十六进制串、UUID、引号内值）+ 原始堆栈顶层帧（文件名去掉构建哈希）。服务端失败的指纹为路由模板 + 错误码；失败提示为页面 + 错误码。
- 同一用户同一指纹 1 分钟内的重复只累加 `repeat_count`，不新增样本。

**员工反馈（OB15）：** `POST /api/runs/{runId}/problem-reports`，只能报告自己能看到的运行；带运行编号与最近的 `trace_id`，说明可选，按员工每小时 20 条限流。每条反馈单独成组（不归并），来源 `feedback`。

### 6.3 脱敏

`http-error-log.ts` 中的 `diagnosticMessage` 目前是模块私有函数；提取到 `server/src/security/safe-observability.ts`，服务端日志、服务端入库与浏览器上报三条路径共用。浏览器上报的消息与堆栈在服务端再脱敏一次，并额外去掉堆栈中的完整网址（只保留文件名与行列号）。员工反馈的说明同样脱敏后保存。

### 6.4 源码映射（OB7）

两端 Vite 构建改为 `build.sourcemap: 'hidden'`；发布打包时把 `.map` 移出前端静态目录，放到 Release 的服务端目录。管理员打开错误详情时，服务端按样本的 `release` 找到对应映射还原堆栈（只读文件，结果缓存）；找不到映射（开发构建或旧版本）时显示原始堆栈并标注。

### 6.5 管理端页面（OB2、OB5、OB9、OB11）

新增两个页面，模块 `ops`，只读：“使用情况”放在导航分组“运行治理”，“错误记录”放在“安全与运维”（OB11）。与“运营概览”的分工：概览看**此刻**（实时运行状态、待关注事项），这两页看**一段时间**。

**使用情况**（路由 `/usage`；周期：近 7 / 30 / 90 天或自选）：

- 指标：活跃员工数（期间内有会话活动或页面访问的人数）、日均活跃、新建对话数、运行数与成功率、Token 消耗。
- 趋势：日活跃员工与日运行数。
- 分布：AI 同事使用排行、入口分布（个人对话、项目空间、定时任务、钉钉）、页面访问排行、按部门的活跃人数与覆盖率、运行失败原因排行（`run_attempts.error_code`）。
- **按人明细（OB9）：** 员工列表（可按部门筛选、按姓名搜索），每人显示最近活跃时间、活跃天数、对话数、运行数与成功率、Token、最常用的 AI 同事、最常访问的页面；单独一栏“期间内未使用”列出组织架构中有账号但期间内没有任何活动的员工。点开某人看其每日趋势与功能分布；不展示对话标题与内容，需要排障时跳转 Session 列表。
- 数据来源：`sessions`、`runs`、`run_attempts`、`model_usage_events`、`workspace_activity_events`、`product_events`、组织架构。

**错误记录**（路由 `/errors`）：

- 视图：**问题**（归并后的前端与服务端错误、失败提示、白屏、员工反馈）与**运行问题**（OB14）。
- 筛选：来源（员工端 / 管理端 / 服务端 / 员工反馈）、类型（默认不含“提示”）、周期、版本、员工；按最近发生或次数排序。
- 列表：消息、来源与类型、次数、影响人数、首次与最近发生、最近版本。
- 详情：最近 20 个样本（时间、员工、页面或路由、客户端、版本、链路编号、运行编号、反馈说明），还原后的堆栈；有运行编号的跳转到 Session 列表详情。
- **运行问题：** 按原因汇总失败、超时、取消、空回答的运行，以及工具调用失败或被拒绝的次数（按工具）；点开看具体运行。
- **链路编号查询：** 输入员工报来的链路编号，列出同一编号的服务端失败与浏览器上报；运行失败按 `run_events.trace_id` 一并列出。

## 7. 覆盖范围

“员工在体验上遇到的问题”按来源分类，本方案覆盖情况如下：

| 员工遇到的情况 | 是否覆盖 | 如何覆盖 |
| --- | --- | --- |
| 页面报错、组件渲染失败、脚本异常 | 是 | 全局错误处理器 |
| 接口 5xx、超时、网络失败 | 是 | `ApiError` 上报 + 服务端入库，按链路编号关联 |
| 看到“操作失败/无权限/参数不正确”提示 | 是（OB12） | 统一失败提示入口 |
| 整个页面白屏、升级后打不开 | 是（OB13） | `index.html` 内联脚本与 `vite:preloadError` |
| 登录或钉钉免登失败 | 是（OB6） | 未登录上报 |
| 运行失败、超时、被取消 | 是（已有数据） | 错误记录页“运行问题” |
| 运行成功但没有回答、工具调用失败 | 是（OB14） | 读取已有运行与工具记录 |
| 回答内容错误、答非所问 | 部分（OB15） | 只能靠员工主动报告；员工不报就不知道 |
| 服务进程崩溃 | 是 | 进程异常处理器 |
| 页面慢、回答慢 | **否** | 不在本期（第 2 节），需要时另做性能统计 |
| 员工遇到问题但直接关掉页面，没有任何报错 | **否** | 系统无从得知；页面访问记录只能看出“进来后很快离开” |
| 浏览器禁用脚本或上报请求被网络拦截 | **否** | 上报本身无法送达 |
| 服务整体宕机 | **否** | 上报接口也不可用；靠“系统健康”与部署守护进程，告警留到二期（OB3） |

结论：**有报错、有失败提示、运行失败或员工主动报告的问题**都能被记录和追踪；**性能、无声的放弃、服务整体宕机**仍不在覆盖范围内。
